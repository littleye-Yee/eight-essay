Redis

1Redis 有哪些常见数据类型？分别用在什么场景？

面试现场

Redis 最常用的有五种基础类型。

  • String：最基础，能存字符串、数字、二进制。我一般用它做对象缓存、计数器（INCR）、分布式锁（SET key val NX EX）。
  • Hash：存对象的多个字段，比用 String 存整个 JSON 更省内存，还能单独更新某个字段。典型场景是购物车。
  • List：有序可重复的双向链表，可以做简单消息队列（LPUSH + BRPOP）和时间线。
  • Set：无序去重集合，做点赞去重、共同好友（SINTER）、抽奖。
  • ZSet：带 score 排序，做排行榜、延时队列。

除此之外还有几种扩展类型：Bitmap 做签到打卡、HyperLogLog 做 UV 统计（有 0.81% 误差，但只占 12KB）、GEO 做附近的人、Stream 做更正式的消息队列，支持消费组和 ACK。

完整解析

1）底层编码（追问最集中的地方）

  • SDS（简单动态字符串）：记录了 len 和 alloc，取长度 O(1)；二进制安全（不像 C 字符串遇 \0 截断）；扩容有预分配，减少内存拷贝。
  • quicklist：一个双向链表，每个节点是一个 listpack。既避免了纯链表的指针开销，又避免了单个大 listpack 的连锁更新。
  • Redis 7 用 listpack 彻底替换了 ziplist：ziplist 在中间插入时会引发「连锁更新」（cascade update），最坏 O(n²)，listpack 通过只记录当前节点长度解决了这个问题。

2）为什么 Hash 比 String 存对象省内存

字段少、值短时，Hash 用 listpack 紧凑存储，没有额外 key 的开销（每个 Redis key 都有 dictEntry + robj + SDS 头，约 100 字节）。但字段多或值长时会退化成 hashtable，反而更费内存，必须实测。

3）ZSet 为什么用跳表不用红黑树

  • 跳表实现简单，范围查询（ZRANGE）天然友好，顺着最底层链表走就行。
  • 红黑树范围查询要中序遍历，实现复杂。
  • ZSet 同时挂了一个 dict，保证按成员查 score 是 O(1)。

4）容易答错的点

  • Bitmap、HyperLogLog 严格说不是独立类型，底层就是 String。
  • GEO 底层是 ZSet，用 geohash 编码当 score。
  • Stream 是 5.0 引入的，有 Consumer Group、PEL（待确认消息列表）、ACK，比 List 做队列可靠得多。
追问预警
  • Q：List 做消息队列有什么问题？
    A：不支持消费组、没有 ACK、多个消费者并发消费时消息会丢（BRPOP 抢到就出队了）。要可靠性就用 Stream，或者直接上专业 MQ。
  • Q：HyperLogLog 为什么能这么省内存？
    A：概率基数估计。把元素哈希后按前导零个数分桶，取每桶最大值，最后做调和平均。标准误差 0.81%，固定 12KB，不能取回元素。
  • Q：Redis 为什么是单线程还这么快？
    A：纯内存操作、IO 多路复用（epoll）、单线程避免了锁和上下文切换、高效的数据结构。注意 6.0 之后网络 IO 是多线程的，命令执行仍然是单线程。

2Redis 的内存淘汰策略有哪些？

面试现场

先纠正一个常见混淆：淘汰策略解决的是「内存满了怎么办」，过期删除策略解决的是「过期 key 怎么删」，这是两回事。

淘汰策略一共 8 种，按两个维度分：淘汰范围（所有 key / 只淘汰设了过期时间的 key）× 淘汰算法（LRU / LFU / random / TTL）。

  • noeviction：默认值，不淘汰，写入直接报错。
  • allkeys-lru / volatile-lru：最近最少使用。
  • allkeys-lfu / volatile-lfu：最不经常使用（Redis 4.0 加入）。
  • allkeys-random / volatile-random：随机淘汰。
  • volatile-ttl：优先淘汰快过期的。

实际生产我一般用 allkeys-lru，如果这个实例既有缓存又有不能丢的数据，就用 volatile-lru 加 noeviction 兜底，或者干脆拆实例。

完整解析

1）Redis 的 LRU 是「近似 LRU」

标准 LRU 要维护一个完整链表，内存和性能代价都高。Redis 的做法是：每个对象头里存一个 24 位的 lru 时间戳（秒级），淘汰时随机采样 maxmemory-samples 个 key（默认 5），从里面挑最久没用的删掉。

采样数越大越接近真实 LRU，5 的时候已经很接近了，10 基本一致。这是个典型的用精度换性能的取舍。

2）LFU 是怎么回事

LFU 用 8 位 counter 记录访问频率（不是简单计数，是对数递增，0-255，越往上越难涨），另 16 位记录最后衰减时间。

为什么需要 LFU？因为 LRU 有个硬伤：一次全表扫描就能把整个热数据冲掉（比如后台跑了个 KEYS * 或者冷数据批量导入）。LFU 按频率淘汰，能扛住这种突发流量。

3）怎么监控和调优

redis-cli info stats | grep evicted_keys   # 被淘汰的 key 总数，>0 说明内存不够了
config set maxmemory 4gb
config set maxmemory-policy allkeys-lru

4）一个真实坑

如果所有 key 都没设过期时间，volatile-lru 会退化成 noeviction——一个都淘汰不了，写操作全部报错。线上出过这个事故，所以要么统一给 key 设 TTL，要么直接用 allkeys-*。

追问预警
  • Q：LRU 和 LFU 怎么选？
    A：访问模式是「最近用过的还会再用」→ LRU；是「用得多的会继续用」→ LFU。有周期性批量任务、冷热分明的场景优先 LFU。
  • Q：淘汰和过期是同一个线程做的吗？
    A：都在主线程里，淘汰发生在命令执行前的内存检查阶段，所以会阻塞主线程——这也是为什么大 key 很危险。

3Redis 的过期删除策略是什么？

面试现场

Redis 用的是惰性删除 + 定期删除的组合，因为单用哪一个都有问题。

  • 惰性删除：访问 key 的时候才检查是否过期，过期就删掉并返回 nil。问题是如果一个 key 再也不被访问，它就永远占着内存。
  • 定期删除：Redis 默认每秒跑 10 次（hz 配置，默认 10，即每 100ms 一次），每次从设置了过期时间的 key 里随机抽 20 个，删掉其中过期的；如果这 20 个里过期比例超过 25%，就再抽 20 个继续，直到比例低于 25% 或者超时（默认 25ms）。

这样组合下来，内存不会无限膨胀，也不会因为一次性扫描全部 key 而卡住。

完整解析

1）为什么不用定时删除

给每个 key 起一个定时器，到点就删——内存最及时，但 CPU 代价极高，几百万个 key 就是几百万个定时器，完全不现实。

2）定期删除的关键参数

hz 10                          # 每秒执行次数，默认 10
active-expire-effort 1         # 1~10，越大越积极，CPU 占用越高

Redis 6.0 后支持 hz 动态调整（dynamic-hz yes），空闲时降低频率省 CPU。

3）过期 key 在从库上怎么处理

这是一个高频追问。从库不主动删除过期 key，它等主库的 DEL 命令同步过来才删。但在主库的 DEL 到达之前，从库读到过期 key 会返回什么？

  • Redis 3.2 之前：直接返回数据（读到脏数据）。
  • Redis 3.2 之后：从库在读取时会判断逻辑过期，返回 nil，但物理上不删，等主库的 DEL。

这是为了保证主从数据一致。

4）和内存淘汰的配合

过期 key 不会立刻被删，所以 used_memory 可能一直贴着 maxmemory。这时淘汰策略就会介入，把还没被定期删除清理掉的 key 淘汰掉。两者是兜底关系，不是二选一。

追问预警
  • Q：如果定期删除和惰性删除都没删掉，内存满了怎么办？
    A：走内存淘汰策略（上一题），所以生产上 maxmemory-policy 一定要配，不能留 noeviction。
  • Q：hz 调大会有什么影响？
    A：定期删除更及时，但主线程 CPU 占用升高。一般不建议超过 100。

4Redis 的持久化策略有哪些？

面试现场

Redis 有两种持久化方式，现在生产上基本是两者混用。

  • RDB（快照）：把某一时刻的全量数据二进制写进磁盘。触发方式有 save（阻塞）、bgsave（fork 子进程，主进程继续服务）、还有配置的自动触发（比如 900 秒内 1 次修改）。恢复快、文件小，但会丢最后一次快照之后的数据。
  • AOF（追加日志）：把每条写命令追加到文件末尾。丢数据少，appendfsync everysec 最多丢 1 秒。但文件大、恢复慢。

Redis 4.0 之后有混合持久化（aof-use-rdb-preamble yes）：AOF 重写时，先写一个 RDB 格式的全量快照作为 AOF 文件头，后面再追加增量命令。这样既恢复快又丢得少，是目前的最优解。

完整解析

1）bgsave 的 fork + COW 机制

fork() 出来的子进程和父进程共享内存页，靠写时复制（Copy-On-Write）：父进程要修改某一页时，才把这页复制一份出来改，子进程仍然读旧页。

所以：

  • fork 本身会阻塞主线程，阻塞时间和内存页表大小成正比，不是和数据量成正比。内存越大（尤其超过 10G），fork 越慢。
  • 快照期间如果写入非常频繁，会导致大量页被复制，内存可能膨胀到 2 倍。这是 bgsave 最需要注意的点。

2）AOF 的三种刷盘策略

配置行为丢数据性能
always每条命令都 fsync几乎不丢最差
everysec每秒 fsync 一次（默认）最多丢 1 秒好
no交给操作系统可能丢几十秒最好

生产上 99% 用 everysec。

3）AOF 重写

AOF 会无限膨胀（比如对一个计数器 INCR 一万次，就有一万条命令）。重写就是根据当前内存里的数据，反推出最精简的命令集。

  • bgrewriteaof：fork 子进程重写。
  • 重写期间的新命令会写到 AOF 重写缓冲区，重写完成后追加到新文件。
  • 触发条件：auto-aof-rewrite-percentage 100（比上次重写后大了 100%）+ auto-aof-rewrite-min-size 64mb。

4）恢复顺序

启动时如果同时开了 RDB 和 AOF，优先用 AOF 恢复，因为 AOF 更完整。开了混合持久化后，AOF 文件开头是 RDB，后面是命令，加载时先加载 RDB 部分再回放命令。

5）怎么选

场景选择
纯缓存，丢了能回源只开 RDB，甚至不开
有数据可靠性要求混合持久化（RDB + AOF everysec）
绝对不能丢AOF always + 主从 + 哨兵/Cluster
追问预警
  • Q：fork 的时候主线程会阻塞多久？
    A：和页表大小相关，一般几十到几百毫秒。可以通过 info stats 的 latest_fork_usec 看。大内存实例建议控制单个实例不超过 10G。
  • Q：AOF 文件损坏了怎么恢复？
    A：用 redis-check-aof --fix 修复，会截断最后一条不完整的命令。
  • Q：混合持久化下，从库全量同步用的是 RDB 还是 AOF？
    A：RDB。主从全量同步走的是 RDB 快照，和 AOF 无关。

5Redis 的集群方案有哪些？

面试现场

按演进顺序有三代：主从复制 → 哨兵 → Cluster 分片。

  • 主从复制：一主多从，主写从读。解决读扩展和单点数据备份，但主挂了需要人工切换。
  • 哨兵（Sentinel）：在主从基础上加一组哨兵进程，负责监控、通知、自动故障转移。解决了高可用，但还是单主写入，写能力没法扩展，容量受单机内存限制。
  • Cluster（分片集群）：把数据按 16384 个哈希槽切分到多个主节点上，每个主节点再挂从节点。解决了写扩展和容量问题，官方要求至少 3 主 3 从。

我们现在用的是 Cluster 模式，6 个节点起步，机器多就横向扩。

完整解析

1）主从复制的流程

  • 全量同步：从节点发 PSYNC ? -1，主节点 bgsave 生成 RDB 发给从节点，同时把期间的写命令写进 repl_backlog_buffer，RDB 传完后把 backlog 里的命令补发过去。
  • 增量同步：从节点带 runid + offset 发 PSYNC，主节点判断 offset 是否还在 repl_backlog_buffer 里，在就只补发差量。
  • 关键参数：repl-backlog-size（默认 1MB，太小会导致频繁全量同步，生产建议调大到几十 MB）、repl-diskless-sync（无盘复制，适合磁盘慢的场景）。

2）哨兵的故障转移流程

  1. 主观下线（SDOWN）：单个哨兵发现主节点 down-after-milliseconds 内没响应。
  2. 客观下线（ODOWN）：超过 quorum 个哨兵都认为它挂了。
  3. 选举 Leader：哨兵之间基于 Raft 算法选出 Leader 来执行故障转移。
  4. 选新主：从从节点里按优先级（replica-priority）→ 复制偏移量最大 → runid 最小 的顺序挑一个。
  5. 通知：让其他从节点 replicaof 新主，并通知客户端（哨兵模式客户端要连哨兵拿主节点地址）。

3）Cluster 的关键机制

  • 16384 个槽：为什么是 16384 而不是 65536？因为槽位图用 Bitmap 表示，16384 位 = 2KB，gossip 消息里每次心跳都要带槽位图，太大浪费带宽；而且 Redis 节点数一般不超过 1000 个，16384 够用。
  • 路由：客户端算 CRC16(key) % 16384 得到槽，连错节点会返回 MOVED（槽已永久迁移）或 ASK（槽正在迁移中，本次去目标节点问）。
  • Gossip 协议：节点间互相通信，交换槽位信息和节点状态。
  • 限制：Cluster 下跨槽的多 key 操作不支持（MGET 多个不同槽的 key 会报错），要用 hash tag {user:1}:name、{user:1}:age 强制落到同一个槽。

4）选型建议

规模方案
数据量小、只要高可用主从 + 哨兵
数据量大、需要写扩展Cluster
只是缓存，能容忍重建主从就够，甚至单机
追问预警
  • Q：Cluster 能不能保证强一致？
    A：不能。Redis 主从复制是异步的，主节点写入后立刻返回客户端，还没来得及同步给从库就挂了，数据就丢了。Cluster 用的是 WAIT 命令可以做到同步等待，但性能下降。要强一致得用 RedLock 那套或者别的方案。
  • Q：哨兵集群本身会不会脑裂？
    A：会。经典场景：主节点和哨兵网络分区，哨兵选出了新主，但老主还在接受写入，恢复后老主降级为从库，这期间的写入就丢了。Redis 用 min-replicas-to-write 参数缓解——主库发现可写从库少于 N 个就拒绝写入。

6什么是缓存击穿？怎么解决？

面试现场

缓存击穿：某个热点 key 突然过期了，大量并发请求同时打到数据库上。注意是「一个热点 key」，这点要和雪崩区分开。

解决方案两个思路：

  1. 互斥锁：缓存失效时，只让一个线程去查数据库并回填缓存，其他线程等待重试。用 SET lock NX EX 实现。
  2. 逻辑过期：key 永不过期，但 value 里存一个逻辑过期时间。发现逻辑过期后，一个线程异步去更新，其他线程先返回旧数据。

选哪个看业务：要求强一致用互斥锁（会短暂阻塞），能容忍短暂脏数据用逻辑过期（不阻塞，吞吐高）。秒杀、热搜榜这种场景我用逻辑过期。

完整解析

1）互斥锁方案代码骨架

public String get(String key) {
    String val = redis.get(key);
    if (val != null) return val;

    String lockKey = "lock:" + key;
    // SET NX EX 保证只有一个人拿到锁
    boolean locked = redis.set(lockKey, "1", "NX", "EX", 10);
    if (locked) {
        try {
            val = redis.get(key);          // 双重检查，防止重复查库
            if (val == null) {
                val = db.query(key);
                redis.set(key, val, 3600);
            }
            return val;
        } finally {
            redis.del(lockKey);
        }
    } else {
        Thread.sleep(50);                  // 没抢到锁，稍后重试
        return get(key);
    }
}

关键点：

  • SET NX EX 是原子的，不能用 SETNX + EXPIRE 两步（中间挂了就死锁）。
  • 必须双重检查，否则锁释放后一堆线程会重复查库。
  • 锁一定要有过期时间，防止持锁线程崩溃导致死锁。

2）逻辑过期方案

class CacheData {
    Object data;
    long expireAt;   // 逻辑过期时间戳
}

线程发现 expireAt 已过，就 tryLock 抢一个更新锁，抢到的开异步线程去查库更新，然后立刻返回旧数据；抢不到的也直接返回旧数据。所有请求都不会阻塞。

3）两个方案的取舍

维度互斥锁逻辑过期
一致性强（拿到的一定是新数据）弱（可能返回旧数据）
阻塞会阻塞（等锁）不阻塞
吞吐低高
实现复杂度低高（要额外存过期时间、异步线程池）
额外风险锁误删（要用 Lua 校验 value）异步更新失败会一直返回旧数据

4）锁误删问题

线程 A 拿锁后卡了很久，锁自动过期了，线程 B 拿到锁，这时 A 执行完 del 把 B 的锁删了。解决：value 存唯一标识（比如 UUID），用 Lua 脚本校验后再删。

追问预警
  • Q：击穿和穿透、雪崩怎么区分？
    A：击穿是「一个热点 key 过期」；穿透是「查一个根本不存在的数据」，每次都打到库；雪崩是「大量 key 同时过期」或者「Redis 整体挂了」。三个词分别对应单点、不存在、批量。
  • Q：热点 key 怎么发现？
    A：redis-cli --hotkeys（基于 LFU）、或者 MONITOR 采样、或者客户端埋点统计。

7什么是缓存穿透？怎么解决？

面试现场

缓存穿透：请求的数据在缓存和数据库里都不存在。缓存查不到就查库，库也查不到，返回空；下次同样的请求又来，还是查库。如果是恶意攻击（比如用不存在的 ID 疯狂刷），数据库直接被打挂。

三个解决办法：

  1. 缓存空值：查库为空也缓存起来，设个短过期时间（比如 60 秒）。实现最简单，缺点是如果攻击者每次用不同的随机 key，会缓存大量垃圾数据。
  2. 布隆过滤器：把所有存在的 key 提前放进布隆过滤器，请求先过过滤器，不存在的直接返回。内存占用极小，缺点是有误判（说不存在的一定不存在，说存在的不一定存在），而且不支持删除。
  3. 参数校验：接口层做基础校验，比如 ID 必须为正整数、格式必须合法，直接挡掉一批垃圾请求。

生产上一般是组合用：参数校验 + 布隆过滤器做前置，再配合空值缓存兜底。

完整解析

1）布隆过滤器原理

用一个位数组 + k 个哈希函数。插入元素时，k 个哈希函数算出 k 个位置，全部置 1。查询时，如果有一个位置是 0，说明一定不存在；如果全是 1，说明可能存在（可能是别的元素把这几个位置置 1 了，这就是误判）。

  • 误判率由位数组大小 m、元素个数 n、哈希函数个数 k 决定。公式：k = m/n * ln2 时最优。
  • 1 亿个元素、误判率 1% 大概需要 114MB（约 9.6 位/元素）；误判率 0.1% 大概需要 171MB。相比存原始数据，省了 90% 以上。
  • 不支持删除：因为一个位置可能被多个元素共用，删了会影响别人。要支持删除就用计数布隆过滤器（Counting Bloom Filter）或者 布谷鸟过滤器。

2）Redis 里的实现

  • RedisBloom 模块：BF.ADD、BF.EXISTS、BF.RESERVE。
  • Redisson：RBloomFilter，底层用 Bitmap 实现。
  • Guava：BloomFilter，单机内存版，重启就没了，需要配合预热。

3）空值缓存的坑

  • 攻击者用随机 key 攻击时，空值缓存会把 Redis 内存打满。所以：
    • 空值 TTL 要短（几十秒到几分钟）。
    • 最好加个前缀区分，或者用单独的实例存。
    • 配合限流（IP 维度、接口维度）。

4）更彻底的方案

  • 接口层限流 + 黑名单：Sentinel / 网关层做 IP 黑名单。
  • 数据预热 + 异步加载：热点数据全量预加载到布隆过滤器。
  • 对于必然不存在的 ID：比如自增 ID 的查询，直接用 id > maxId 判断，成本最低。
追问预警
  • Q：布隆过滤器怎么预热？
    A：启动时或定时任务把数据库里的 key 全量扫一遍 BF.ADD。要注意新增数据时同步写过滤器，一般通过 binlog 订阅（Canal）来做，避免业务代码里到处埋点。
  • Q：布隆过滤器能不能判断「一定存在」？
    A：不能。它只能保证「不存在的一定不存在」，判断存在有误判概率。这是面试高频考点，一定要说清方向。

8什么是缓存雪崩？怎么解决？

面试现场

缓存雪崩：大量缓存 key 在同一时间集中失效，或者 Redis 整个实例/集群挂了，导致请求全部涌向数据库，数据库瞬间被打挂，进而引发整个系统雪崩。

解决思路分两类：

针对「同时失效」：

  1. 过期时间加随机值：在基础 TTL 上加一个随机偏移，比如 3600 + Random(0, 600)，把失效时间打散。
  2. 多级缓存：本地缓存（Caffeine）+ Redis，Redis 挂了本地还能顶一阵。
  3. 缓存预热 + 永不过期：热点数据逻辑过期，异步更新。

针对「Redis 挂了」：

  1. 集群高可用：主从 + 哨兵 / Cluster，避免单点。
  2. 熔断降级：Sentinel / Hystrix 对数据库访问做限流，宁可返回兜底数据也不能打挂库。
  3. 数据库层兜底：读写分离、连接池隔离。

核心一句话：不要让缓存层成为单点，也不要让所有 key 同时失效。

完整解析

1）雪崩 vs 击穿 vs 穿透 对比

问题触发条件影响范围核心解法
穿透查不存在的数据单个（可被放大成攻击）布隆过滤器 + 空值缓存
击穿单个热点 key 过期单个热点互斥锁 / 逻辑过期
雪崩大量 key 同时过期 / Redis 挂整体随机 TTL + 高可用 + 降级

2）过期时间打散的实现

// 错误做法：所有 key 同一时间过期
redis.set(key, val, 3600);

// 正确做法：基础时间 + 随机抖动
int ttl = 3600 + ThreadLocalRandom.current().nextInt(600);
redis.set(key, val, ttl);

更好的做法是分级 TTL：热点数据 1 小时，普通数据 6 小时，冷数据 24 小时，天然错开。

3）多级缓存架构

请求 → Caffeine 本地缓存（毫秒级）→ Redis（毫秒级）→ MySQL（几十毫秒）
  • 本地缓存容量小但极快，抗住 Redis 挂掉后的第一波流量。
  • 难点是本地缓存的一致性：一般通过 MQ 广播失效消息，或者接受短暂不一致（设很短的 TTL）。

4）熔断降级的落地

  • Sentinel 配置数据库访问的 QPS 阈值，超了直接快速失败返回兜底数据。
  • 降级策略：返回默认值、返回缓存旧值、返回排队页。
  • 原则：宁可让 10% 的用户看到兜底页，也不能让数据库挂掉导致 100% 的用户不可用。

5）生产上的组合拳

1. TTL 随机化           → 防同时失效
2. Redis 主从 + 哨兵    → 防单点
3. 本地缓存二级         → 防 Redis 全挂
4. Sentinel 限流降级    → 防数据库被打挂
5. 提前预热（大促前）    → 防冷启动
追问预警
  • Q：Redis 集群挂了一半，怎么保证服务可用？
    A：Cluster 模式下，只要某个槽的主从都挂了，这个槽就不可用。缓解方式是：cluster-require-full-coverage no（部分槽不可用时其他槽仍能服务），加上客户端对失败 key 做降级处理。
  • Q：本地缓存怎么保证多台机器数据一致？
    A：一般靠 MQ 广播失效 + 短 TTL 兜底。要求强一致就别用本地缓存，这是设计取舍。

9Redis 和数据库的数据同步怎么做？（缓存一致性）

面试现场

这是 Redis 最容易被深挖的题，因为没有任何方案能做到强一致，只能做到最终一致。

主流方案有三种，按可靠性排序：

  1. 先更新数据库，再删除缓存（Cache Aside）：最常用。问题是并发下可能产生脏数据。
  2. 延迟双删：更新库 → 删缓存 → 等一会（比如 500ms）→ 再删一次缓存。解决「删缓存和更新库之间的并发窗口」。
  3. 订阅 binlog 异步删除（Canal）：业务代码只更新数据库，Canal 监听 binlog 投到 MQ，消费者删缓存。业务解耦、最可靠，也是大厂主流方案。

为什么不推荐「更新缓存」而是「删除缓存」？因为更新缓存有两个问题：一是并发更新时可能写入旧值；二是如果这个缓存值计算复杂，每次更新都算一遍很浪费（读多写少时，删了等下次读再回填更划算）。

完整解析

1）先删缓存还是先更新库？

方案并发问题结论
先删缓存，再更新库A 删了缓存，B 读缓存未命中→读库旧值→写回缓存；A 才更新完库。缓存里是旧值且长期存在不推荐
先更新库，再删缓存A 更新库，B 读缓存（还是旧值，因为 A 还没删）→ 返回旧值；A 删缓存。只影响这一次读，后续读会回源推荐

所以「先更新库再删缓存」的不一致窗口非常短（就是 A 更新完到删缓存之间的几十毫秒），而且下次读就会修正。

2）那为什么还要延迟双删？

「先更新库再删缓存」的极端情况：读请求 B 在缓存失效后读库（读到旧值），但在写回缓存之前被卡住了（比如 GC 或者网络延迟），此时 A 更新完库并删了缓存，然后 B 才把旧值写回缓存 —— 缓存里就是永久的旧值了。

延迟双删就是：删一次缓存 → 更新库 → 睡 500ms → 再删一次缓存。第二次删是为了清掉那个「迟到的旧值」。

但延迟双删有两个硬伤：

  • 睡眠时间靠猜，睡多久都可能不够。
  • 同步睡眠会拖慢接口响应。要用异步线程池或者延时队列。

3）Canal + MQ 方案（推荐）

业务更新 MySQL → binlog → Canal 解析 → MQ → 消费者删 Redis

优点：

  • 业务代码零侵入，只更新数据库。
  • 顺序有保证（同一行的 binlog 是顺序的），不会出现乱序。
  • 数据库更新成功才删缓存，不会出现「库没更新但缓存删了」。
  • 可以顺便做数据同步到 ES、从库等。

缺点：架构复杂，引入 Canal + MQ 组件，有延迟（通常几十到几百毫秒）。

4）如果业务能接受强一致怎么办

  • 读写都加分布式锁（Redisson），但性能极差，一般不用。
  • 关键数据不走缓存，或者缓存只做「降级兜底」（比如库存，直接读库加行锁）。
  • 用 SETNX 做并发控制，保证同一时刻只有一个线程能回源。

5）面试怎么说才加分

"严格意义上缓存和数据库无法做到强一致，除非加分布式锁把读写串行化，但那会牺牲性能。工程上我们追求最终一致，用 Canal 订阅 binlog 异步删缓存，正常延迟在 100ms 内。业务上通过给缓存设置 TTL 兜底，即使出现极端的不一致，最多 TTL 时间后也会自动修正。"

这段话体现的是知道边界、会做取舍，比背方案更有说服力。

追问预警
  • Q：为什么不用「更新缓存」？
    A：并发写会互相覆盖（A 写 1、B 写 2，最后缓存可能是 1）；而且如果缓存值需要多表聚合计算，每次写都重算代价太高。
  • Q：删缓存失败了怎么办？
    A：这是「先更新库再删缓存」的致命问题——删失败就永久不一致。解法：删除失败重试（把失败消息投到 MQ 重试队列），或者直接用 Canal 方案（binlog 保证不丢）。
  • Q：Redis 挂了，写请求怎么办？
    A：写请求一般直接写库，缓存只是读加速。但要注意 Redis 挂的时候读请求全部回源会打挂库，必须有降级。

10讲一下 JVM 的类加载机制

面试现场

类加载分加载、验证、准备、解析、初始化五个阶段，其中验证、准备、解析合称连接。

  • 加载：把 class 文件的二进制字节流读进内存，生成 Class 对象。
  • 验证：文件格式、元数据、字节码、符号引用四层校验，防止恶意代码。
  • 准备：给静态变量分配内存并设零值（static int a = 10 此时 a 是 0，不是 10）。
  • 解析：把常量池里的符号引用替换成直接引用。
  • 初始化：执行 <clinit> 方法，也就是静态变量的赋值和静态代码块。这一步才真正把 a 变成 10。

加载的触发时机是初始化阶段才会真正触发，有且只有 5 种情况（主动引用）：new、访问静态字段/方法、反射、初始化子类时先初始化父类、作为启动类（main 所在类）。

然后是双亲委派模型：类加载请求先交给父加载器，父加载器加载不了才自己加载。三层是 Bootstrap（rt.jar 等核心类）→ Extension/Platform（jre/lib/ext）→ Application（classpath）→ 自定义。

作用：一是保证安全，用户自己写的 java.lang.String 永远不会被加载，因为 Bootstrap 已经加载过了；二是避免重复加载。

完整解析

1）双亲委派的源码逻辑

protected Class<?> loadClass(String name, boolean resolve) {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);      // 1. 先查自己加载过没
        if (c == null) {
            try {
                if (parent != null) {
                    c = parent.loadClass(name, false);   // 2. 委派父加载器
                } else {
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) { }
            if (c == null) {
                c = findClass(name);              // 3. 父加载不了，自己加载
            }
        }
        return c;
    }
}

注意：双亲委派是「优先委派」，不是「必须委派」。重写 loadClass 就能打破它。

2）怎么打破双亲委派

场景做法
SPI 机制（JDBC、SPI 加载第三方实现）用 Thread.currentThread().getContextClassLoader()，即线程上下文类加载器
Tomcat每个 webapp 一个 WebappClassLoader，先自己加载，加载不到才给父加载器（打破了「先委派」的顺序），实现应用隔离
OSGi / 热部署自定义加载器 + 模块化，实现类的热替换
JDK 9 模块化改成「委派给平台加载器 + 按模块名委派」

Tomcat 为什么打破？ 因为一个 Tomcat 要跑多个 web 应用，每个应用可能依赖同一个库的不同版本，必须隔离。同时 Tomcat 自己的类（比如 Servlet API）又要共享，所以做成「自己优先，但核心类仍委派」。

3）类初始化的六种「被动引用」（不会触发初始化）

  1. 通过子类引用父类的静态字段，只初始化父类。
  2. 通过数组定义引用类：Son[] arr = new Son[10]，不初始化 Son。
  3. 常量在编译期已存入调用类的常量池：static final int A = 1，不初始化定义类。
  4. 通过 Class.forName 的参数控制（initialize=false）。
  5. 加载一个类时，其接口不要求初始化。
  6. 静态字段被 final + 编译期常量优化。

4）<clinit> 的几个特性

  • 线程安全：JVM 保证一个类的 <clinit> 在多线程下只执行一次，其他线程阻塞等待。所以静态内部类单例天然线程安全。
  • 父类先于子类：JVM 保证先执行父类的 <clinit>。
  • 接口不需要：接口的 <clinit> 只有在使用到接口中定义的字段时才执行。
追问预警
  • Q：Class.forName 和 ClassLoader.loadClass 有什么区别？
    A：Class.forName 默认会执行初始化（initialize=true），loadClass 只做加载不做初始化。JDBC 驱动注册就是用 Class.forName 触发静态代码块。
  • Q：两个不同类加载器加载同一个 class 文件，得到的 Class 对象相等吗？
    A：不相等。JVM 判断两个类相同的前提是类加载器相同 + 全限定名相同。这是 Tomcat 隔离、OSGi 的基础。
  • Q：静态变量和静态代码块的执行顺序？
    A：按源码顺序执行。父类静态 → 子类静态 → 父类实例变量/代码块 → 父类构造 → 子类实例变量/代码块 → 子类构造。

11讲一下 JVM 的内存结构

面试现场

JVM 运行时数据区分为线程私有和线程共享两部分。

线程私有（随线程创建销毁）：

  • 程序计数器：记录当前线程执行到哪条字节码。唯一不会 OOM 的区域。
  • 虚拟机栈：每个方法对应一个栈帧，存局部变量表、操作数栈、动态链接、方法出口。栈溢出报 StackOverflowError。
  • 本地方法栈：给 native 方法用。

线程共享（随 JVM 启动创建）：

  • 堆：对象实例主要分配在这里，GC 的主战场。分新生代（Eden + 两个 Survivor，默认 8:1:1）和老年代，默认比例 1:2。
  • 方法区：存类元信息、常量、静态变量。JDK 8 之后用元空间（Metaspace）实现，放在本地内存而不是堆里，受 MaxMetaspaceSize 限制。

另外还有直接内存（DirectByteBuffer），不受堆大小限制，受物理内存限制。

完整解析

1）为什么 JDK 8 要把永久代换成元空间

  • 永久代在堆里，大小受 -XX:MaxPermSize 限制，容易 OutOfMemoryError: PermGen space。
  • 永久代大小难以预估，类多（比如动态代理、大量 JSP）就容易撑爆。
  • 元空间用本地内存，理论上只受物理内存限制，而且由类加载器生命周期管理，类加载器被回收时元空间就释放。

2）堆的分代与参数

-Xms4g -Xmx4g                    # 堆初始/最大，建议设成一样避免动态扩容
-XX:NewRatio=2                   # 老年代:新生代 = 2:1
-XX:SurvivorRatio=8              # Eden:Survivor = 8:1:1
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=256m
-XX:MaxDirectMemorySize=1g
-Xss1m                           # 每个线程栈大小

为什么新生代用 8:1:1？ 因为大部分对象朝生夕死（弱分代假说），需要留出足够大的 Eden，Survivor 只需要够放「活过一次 GC」的对象。

3）对象创建到分配的完整流程

  1. 检查类是否加载，没加载就先加载。
  2. 分配内存：指针碰撞（内存规整）或空闲列表（内存碎片化）。并发下用 CAS + 失败重试 或者 TLAB（每个线程在 Eden 里预分配一块私有区域）保证安全。
  3. 初始化零值。
  4. 设置对象头：Mark Word（哈希码、GC 分代年龄、锁标志位）+ 类型指针。
  5. 执行构造方法。

对象的内存布局：对象头 + 实例数据 + 对齐填充（保证是 8 字节的整数倍）。

4）逃逸分析带来的两个优化

如果 JVM 分析出对象不会逃逸出方法（没被返回、没被其他线程引用），可以：

  • 栈上分配：直接在栈上分配，随方法结束自动回收，不经过 GC。
  • 标量替换：把一个对象拆成几个基本类型变量。

这两个优化需要开启逃逸分析（JDK 7 后默认开启，Server 模式）。

  • Q：栈和堆的区别？
    A：栈是线程私有、生命周期短、存局部变量和方法调用、分配快；堆是线程共享、生命周期由 GC 管、存对象实例、分配相对慢。

12讲一下 JVM 的垃圾回收机制

面试现场

我按「怎么判断垃圾 → 怎么回收 → 用什么回收」三步讲。

一、怎么判断是垃圾用可达性分析，从 GC Roots 出发，能走到的对象就是活的。GC Roots 包括：虚拟机栈里引用的对象、静态变量引用的对象、常量引用的对象、JNI 引用的对象、被同步锁持有的对象。

不用引用计数法，因为它解决不了循环引用。

二、垃圾回收算法

  • 标记-清除：会产生内存碎片。
  • 复制：把存活对象复制到另一块，无碎片但浪费一半空间。用于新生代。
  • 标记-整理：标记后把存活对象往一端挪，无碎片但慢。用于老年代。

三、分代回收

  • 新生代：对象优先在 Eden 分配，满了触发 Minor GC。存活对象进 Survivor，每熬过一次 GC 年龄 +1，默认到 15 岁晋升老年代。还有动态年龄判定：Survivor 里相同年龄对象总和超过一半，直接晋升。
  • 老年代：存不下触发 Full GC（也叫 Major GC）。Full GC 会 STW，要尽量避免。

四、垃圾收集器主流是 G1（JDK 9 起默认），大内存低延迟场景可以用 ZGC。

完整解析

1）为什么不用引用计数

a.b = b; b.a = a; 把 a、b 置 null 后，两个对象的引用计数都是 1，永远回收不掉。可达性分析从根出发，就不会有这个问题。

2）对象「死亡」的两次标记

可达性分析判定不可达后，还有一次自救机会：如果对象重写了 finalize() 且没被执行过，会被放进 F-Queue 队列，由一个低优先级线程执行 finalize()。如果在这个方法里重新和 GC Roots 建立引用，就能活下来。

注意：finalize() 已被废弃（JDK 9 deprecated，JDK 18 标记为 deprecated for removal），别在业务里用。

3）三色标记法（并发标记的核心）

CMS 和 G1 都是并发标记（GC 线程和用户线程同时跑），这就有个问题：标记过程中对象引用关系变了怎么办？

  • 漏标：一个黑色对象新增了对白色对象的引用，且灰色对象到白色对象的引用被删除 → 白色对象会被漏掉。
  • 错标：把活对象标成垃圾。

解决办法是读写屏障：

方案做法谁在用
增量更新（Incremental Update）记录黑色对象新增的引用，重新扫描CMS
原始快照（SATB, Snapshot At The Beginning）记录被删除的引用，按开始时的快照标记G1、Shenandoah

记忆点：CMS 用增量更新（管新增），G1 用 SATB（管删除）。

4）收集器对比

5）CMS 的四个阶段

  1. 初始标记（STW，很短）：只标记 GC Roots 直接关联的对象。
  2. 并发标记（不 STW，最长）：从根遍历整个对象图。
  3. 重新标记（STW）：修正并发期间变动的记录，用增量更新。
  4. 并发清除（不 STW）：清除垃圾对象。

CMS 的三个问题：

  • 内存碎片：标记-清除不整理，碎片多了提前触发 Full GC。用 -XX:+UseCMSCompactAtFullCollection 缓解。
  • 浮动垃圾：并发清除时新产生的垃圾只能等下次。
  • Concurrent Mode Failure：并发清理时老年代不够用了，退化成 Serial Old 单线程 Full GC，停顿会很长。用 -XX:CMSInitiatingOccupancyFraction 提前触发。

6）G1 的核心设计

  • Region 化：把堆分成大小相等的 Region（1~32MB，2 的幂），每个 Region 动态扮演 Eden/Survivor/Old/Humongous（大对象）。
  • 可预测停顿：-XX:MaxGCPauseMillis=200，G1 根据每个 Region 的回收收益（垃圾占比）排序，优先回收收益高的 Region，这就是 Garbage First 的由来。
  • 回收模式：Young GC（只回收新生代 Region）、Mixed GC（新生代 + 部分老年代）、Full GC（兜底，JDK 10 后是并行 Full GC）。
  • 记忆集 + 卡表：跨 Region 引用用 Remembered Set 记录，避免全堆扫描。写屏障维护卡表。
  • 大对象：超过 Region 一半的对象直接进 Humongous Region，连续占用，容易引发 Full GC，要尽量避免。

7）线上排查 GC 问题的常用手段

# 看 GC 概览

# 看堆直方图

# dump 堆
jmap -dump:live,format=b,file=heap.hprof <pid>
# 然后用 MAT / JProfiler 分析

关键指标：Young GC 频率（几秒一次正常，几百毫秒一次就有问题）、Full GC 频率（理想是几天甚至几周一次，一天几次就是事故）、单次停顿时间。

追问预警
  • Q：Minor GC、Major GC、Full GC 的区别？
    A：Minor GC 只回收新生代；Major GC 只回收老年代（通常伴随一次 Minor，所以也常被叫 Full GC）；Full GC 回收整个堆 + 元空间 + 直接内存，最慢，要尽量避免。
  • Q：什么时候对象会直接进老年代？
    A：① 大对象直接进（-XX:PretenureSizeThreshold）；② 长期存活对象年龄到 15；③ 动态年龄判定；④ Survivor 空间不足，分配担保机制触发。
  • Q：什么是空间分配担保？
    A：Minor GC 前，JVM 检查老年代最大可用连续空间是否大于新生代所有对象总大小，不够就看是否允许担保失败，允许就冒险 GC，否则直接 Full GC。
  • Q：什么情况会触发 Full GC？
    A：老年代空间不足、元空间不足、调用 System.gc()（有 -XX:+DisableExplicitGC 可以禁掉）、CMS 的 Concurrent Mode Failure、担保失败。

13ArrayList 的底层原理？为什么线程不安全？

面试现场

ArrayList 底层就是一个 Object 数组。

  • 默认容量：不指定的话是空数组，第一次 add 时才扩成 10（DEFAULT_CAPACITY）。
  • 扩容：满了之后按 1.5 倍扩（oldCapacity + (oldCapacity >> 1)），然后 Arrays.copyOf 把老数据拷过去。
  • 随机访问 O(1)，中间插入/删除 O(n)，因为要移动后面所有元素。
  • 线程不安全：多线程 add 会丢数据、数组越界、甚至出现 null。

要线程安全可以用 Collections.synchronizedList、CopyOnWriteArrayList，或者干脆用锁自己控制。

完整解析

1）扩容的细节

private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);   // 1.5 倍
    if (newCapacity - minCapacity < 0)
        newCapacity = minCapacity;                        // 至少满足本次需求
    if (newCapacity - MAX_ARRAY_SIZE > 0)
        newCapacity = hugeCapacity(minCapacity);          // 处理 int 溢出
    elementData = Arrays.copyOf(elementData, newCapacity);
}

为什么是 1.5 倍而不是 2 倍？

  • 2 倍浪费空间更多。
  • 1.5 倍在「扩容次数」和「空间浪费」之间比较平衡。
  • 还有个说法是：1.5 倍的情况下，之前释放的空间有可能被复用（因为总大小按 1.5 倍增长，前面几轮释放的内存加起来能容纳下一次扩容），而 2 倍永远需要一块全新的连续空间。这是内存分配器视角的考量。

2）new ArrayList<>(10) 和 new ArrayList() 的区别

  • new ArrayList<>(10)：直接创建长度 10 的数组。
  • new ArrayList()：创建空数组 DEFAULTCAPACITY_EMPTY_ELEMENTDATA，第一次 add 才扩到 10（懒加载）。

3）JDK 8 里为什么用 DEFAULTCAPACITY_EMPTY_ELEMENTDATA 和 EMPTY_ELEMENTDATA 两个空数组？

为了区分「无参构造」和「指定容量 0 构造」，这样扩容时前者扩到 10，后者扩到 1（DEFAULT_CAPACITY 和 minCapacity 取较大值）。细节但能体现读过源码。

4）线程不安全的具体表现

// 场景一：丢数据
// 两个线程同时执行 elementData[size] = e，后写的覆盖先写的
elementData[size++] = e;
// 这一行不是原子操作，实际是：
// 1. 读 size
// 2. 写 elementData[size]
// 3. size = size + 1
// 线程 A 和 B 都读到 size=5，都往 index 5 写，最后 size 只加了 1 → 丢了一个元素

// 场景二：数组越界
// 线程 A 判断 size=9 < 10 通过，准备扩容；线程 B 也在同一位置写 → ArrayIndexOutOfBoundsException

// 场景三：出现 null
// 扩容时 Arrays.copyOf，另一个线程正好在写 → 读到还没赋值的 null

5）替代方案对比

方案读性能写性能说明
Collections.synchronizedList差（全表锁）差简单粗暴，读也加锁
CopyOnWriteArrayList极好（无锁读）差（每次复制全数组）读多写少才用
Vector差差古老，方法全 synchronized，已不推荐
自己加锁可控可控按业务粒度控制

CopyOnWriteArrayList 的原理：写的时候先加锁，复制一份新数组，在新数组上改，然后把引用指向新数组。读操作完全无锁，读到的一定是某个完整快照。缺点是写代价高、内存翻倍、读到的可能不是最新数据。

追问预警
  • Q：ArrayList 和 LinkedList 怎么选？
    A：ArrayList 随机访问 O(1)、末尾追加快、内存连续（缓存友好）；LinkedList 头尾插入 O(1) 但随机访问 O(n)、每个节点有额外指针开销、内存不连续。实测下来绝大多数场景 ArrayList 更快，即使中间插入，因为数组拷贝是内存连续操作，比链表遍历找位置快得多。除非是频繁的头部插入且数据量很大。
  • Q：ArrayList 的 modCount 是干什么的？
    A：记录结构性修改次数，用于快速失败（fail-fast）。迭代过程中如果 modCount != expectedModCount 就抛 ConcurrentModificationException。注意它不保证检测到所有并发修改，只是「尽力而为」的检查机制。
  • Q：怎么在遍历中安全删除元素？
    A：用 Iterator.remove()，它会同步更新 expectedModCount；或者用 removeIf；或者倒序遍历删除。

14HashMap 的底层原理？JDK 8 做了什么优化？

面试现场

结构：JDK 8 是数组 + 链表 + 红黑树，JDK 7 是数组 + 链表。

核心参数：

  • 默认容量 16，负载因子 0.75，阈值 = 容量 × 0.75。
  • 链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树；红黑树节点数 ≤ 6 时退化回链表。

put 流程：

  1. 计算 hash = (h = key.hashCode()) ^ (h >>> 16)，高位参与运算，让分布更均匀。
  2. (n - 1) & hash 定位桶（n 是 2 的幂，等价于取模但更快）。
  3. 桶为空就放；不为空就遍历，key 相同（hash 相同且 equals 为 true）就覆盖，否则尾插。
  4. 链表长度到 8 就尝试树化。
  5. size > threshold 就扩容成 2 倍。

JDK 8 的三个关键优化：

  1. 链表改尾插（JDK 7 头插在并发扩容时会形成环形链表死循环）。
  2. 引入红黑树，把最坏查询从 O(n) 降到 O(log n)，防止哈希碰撞攻击。
  3. 扩容时不需要重新计算 hash：因为容量是 2 倍，元素要么在原位置，要么在原位置 + 老容量，用 hash & oldCap 一次判断即可，拆成「低位链」和「高位链」两条。
完整解析

1）为什么容量必须是 2 的幂

因为 (n - 1) & hash 要等价于 hash % n，只有 n 是 2 的幂时才成立。而且 n 是 2 的幂时，n-1 的二进制全是 1，能充分利用 hash 的每一位，减少碰撞。

如果传入的初始容量不是 2 的幂，tableSizeFor 会把它向上取整到最近的 2 的幂（比如传 17 得到 32）。

2）扰动函数为什么是 h ^ (h >>> 16)

数组长度通常很小（16、32），(n-1) & hash 实际只用到 hash 的低几位。如果不处理，高位的信息就浪费了。所以把高 16 位异或到低 16 位，让高位也参与运算。

为什么是异或而不是与/或？ 因为异或能同时保留两边的信息（0 和 1 各占 50%），与会偏向 0、或会偏向 1，都会降低随机性。

3）为什么负载因子是 0.75

  • 太小（比如 0.5）：空间浪费一半，扩容频繁。
  • 太大（比如 1.0）：碰撞概率显著上升，链表变长。
  • 0.75 是在空间和时间上的折中，来自泊松分布——在 0.75 的情况下，一个桶里链表长度达到 8 的概率约 0.00000006，也就是几乎不可能，所以树化阈值定在 8。

4）为什么树化阈值是 8、退化是 6

  • 8 是因为正常情况下几乎达不到（见上面的概率），达到了说明哈希函数被恶意攻击或者分布极差，这时用红黑树兜底。
  • 退化用 6 而不是 7，是为了留一个缓冲区间，避免在 7、8 之间反复横跳（树化和退化本身都有开销）。

5）树化为什么要求数组长度 ≥ 64

数组太小的时候，碰撞更可能是容量不足导致的，而不是哈希分布问题。这时优先扩容（扩容后元素会重新分布）比树化更划算。

6）扩容的 rehash 细节（JDK 8 的精妙之处）

// JDK 7：每个元素重新计算 index，还要重新算 hash
int i = indexFor(e.hash, newCapacity);

// JDK 8：只用一次位运算判断
if ((e.hash & oldCap) == 0) {
    // 留在原位置 j
} else {
    // 移到 j + oldCap
}

因为容量从 n 变成 2n，(2n - 1) & hash 比 (n - 1) & hash 多了一个最高位，这个位正好是 hash & oldCap。为 0 就不动，为 1 就往后挪 n 位。所以扩容时把一条链表拆成两条，保持了元素的相对顺序（这也是尾插带来的好处）。

7）HashMap 的线程不安全

  • JDK 7：并发扩容时头插法会导致环形链表，get 时死循环，CPU 飙到 100%。
  • JDK 8：改成尾插，不会成环，但会丢数据（两个线程同时 put 到同一个空桶，后写的覆盖先写的）和 size 不准。

所以并发场景必须用 ConcurrentHashMap。

8）key 为什么要重写 hashCode 和 equals

  • hashCode 决定落在哪个桶。
  • equals 决定桶内是不是同一个 key。
  • 两个 equals 相等的对象，hashCode 必须相等（否则会落在不同桶里，逻辑就错了）。反过来 hashCode 相等，equals 可以不相等（就是碰撞）。
追问预警
  • Q：HashMap 的 get 流程？
    A：算 hash → 定位桶 → 桶为空返回 null → 首节点匹配就返回 → 是树就按树查找 → 是链表就遍历比较，都没找到返回 null。
  • Q：为什么 JDK 8 不用头插了？
    A：头插在并发扩容时会成环。虽然 HashMap 本来就不支持并发，但改成尾插能让「不小心并发使用」的后果从「死循环」降到「丢数据」，危害小得多。
  • Q：HashMap 扩容为什么是 2 倍？
    A：2 倍能保证容量一直是 2 的幂，从而可以用 & 代替取模；同时让 rehash 可以用「拆两条链」的方式完成，不用重算 hash。
  • Q：怎么让 HashMap 线程安全？
    A：Collections.synchronizedMap（全表锁）、ConcurrentHashMap（推荐）、Hashtable（古老，全表锁，已淘汰）。

面试现场

JDK 7：用分段锁 Segment。整个 Map 分成 16 个 Segment，每个 Segment 继承 ReentrantLock，锁的是一个段。理论并发度是 16。

JDK 8：放弃了分段锁，改成 CAS + synchronized 锁单个桶的头节点。

  • 数组 + 链表 + 红黑树（和 HashMap 一样）。
  • 空桶用 CAS 插入（无锁）。
  • 非空桶 synchronized 锁住头节点，锁粒度细化到单个桶，并发度大大提升。
  • size 用 CounterCell 数组做分散计数（借鉴 LongAdder）。
  • 多线程协助扩容：transfer 时用 ForwardingNode 标记已迁移的桶，其他线程可以帮忙一起搬。

为什么 JDK 8 要改？ 分段锁的并发度被 Segment 数量限制死了（默认 16），扩容也不方便。改成锁桶头节点后，并发度等于桶的数量，而且支持多线程协同扩容。

完整解析

1）核心参数

transient volatile Node<K,V>[] table;          // 哈希桶数组，volatile 保证可见性
private transient volatile Node<K,V>[] nextTable;  // 扩容时的新数组
private transient volatile int sizeCtl;        // 控制标识：负数表示正在初始化/扩容

sizeCtl 的含义：

  • 0：默认值，还没初始化。
  • -1：正在初始化。
  • -(1 + n)：正在扩容，n 是参与扩容的线程数。
  • 正数：下次扩容的阈值（容量 × 0.75）。

2）put 的流程

final V putVal(K key, V value, boolean onlyIfAbsent) {
    int hash = spread(key.hashCode());
    for (Node<K,V>[] tab = table;;) {
        if (tab == null) tab = initTable();                    // 1. 懒初始化
        else if ((f = tabAt(tab, i)) == null) {
            // 2. 空桶：CAS 无锁插入，失败就自旋重试
            if (casTabAt(tab, i, null, new Node<>(hash, key, value)))
                break;
        }
        else if (f.hash == MOVED) {
            tab = helpTransfer(tab, f);                        // 3. 正在扩容，帮忙迁移
        }
        else {
            // 4. 非空桶：synchronized 锁住头节点
            synchronized (f) {
                if (tabAt(tab, i) == f) {                      // 双重检查
                    if (f.hash >= 0) { /* 链表插入，尾插 */ }
                    else if (f instanceof TreeBin) { /* 红黑树插入 */ }
                }
            }
        }
    }
    addCount(1L, binCount);   // 5. 计数 + 判断是否需要扩容
}

三个关键点：

  • 空桶 CAS：没有任何锁，性能极高。
  • 非空桶只锁头节点：不同桶的写入完全并行，并发度 = 桶数量。
  • tabAt 用 Unsafe.getObjectVolatile：保证读到的是最新值，而不是工作内存里的旧值。

3）为什么用 synchronized 而不是 ReentrantLock

  • JDK 8 对 synchronized 做了大量优化（偏向锁、轻量级锁、锁消除、锁粗化），在低竞争下性能不比 ReentrantLock 差。
  • synchronized 是 JVM 内置的，内存占用更小（ReentrantLock 每个锁对象都要维护 AQS 队列）。
  • 每个桶都挂一个 ReentrantLock 对象，内存开销太大（桶数量可能是几十万）。

4）size 的统计方式

如果用一个 AtomicLong，高并发下 CAS 会成为瓶颈（大量线程自旋失败）。JDK 8 借鉴 LongAdder：

  • 有一个 baseCount 基础值。
  • 竞争激烈时，创建 CounterCell[] 数组，每个线程哈希到自己那个 cell 上累加，分散竞争。
  • 最终 size() 是 baseCount + 所有 cell 的和。

注意：size() 返回的是「估算值」，因为统计期间可能有并发修改，不保证精确。

5）多线程协同扩容（transfer）

  • 触发扩容的线程创建 nextTable（2 倍大小），sizeCtl 设为 -(1 + n)。
  • 迁移时把老数组的桶分成若干个区间（stride），每个线程领一个区间去搬。
  • 搬完的桶放一个 ForwardingNode（hash = MOVED = -1），其他线程遇到它就知道「这个桶已经搬走了，而且正在扩容」，于是也加入进来帮忙。
  • 每个桶的迁移用 synchronized 锁住，保证安全。
  • 扩容期间读操作会去 nextTable 找，写操作遇到 MOVED 会先帮忙迁移再写。

这个设计的精髓是：扩容不再是「一个线程干，其他线程等」，而是所有人一起干，把 STW 风险降到了最低。

7）几个容易踩的点

  • 不允许 null key / null value：因为 get 返回 null 无法区分「不存在」和「值为 null」，并发下没法用 containsKey 二次确认。
  • 弱一致性迭代器：迭代过程中不抛 ConcurrentModificationException，但可能读不到最新的修改。
  • computeIfAbsent 里不要做耗时操作：会持有桶的锁，阻塞其他线程。
  • 复合操作要用原子方法：if (!map.containsKey(k)) map.put(k, v) 不是原子的，要用 putIfAbsent。
追问预警
  • Q：ConcurrentHashMap 怎么保证可见性？
    A：table 和 Node.val、Node.next 都是 volatile 的；读取用 Unsafe.getObjectVolatile；写入用 CAS 或 synchronized（synchronized 本身有内存屏障语义）。
  • Q：为什么 key/value 不能为 null？
    A：并发场景下没法可靠区分「key 不存在」和「key 存在但值为 null」，containsKey 在并发下也可能被其他线程改掉。

16Spring Boot 自动装配的原理是什么？

面试现场

一句话：Spring Boot 通过 @EnableAutoConfiguration 导入一个 AutoConfigurationImportSelector，它在启动时扫描所有 jar 包里 META-INF/spring.factories（2.7 之后是 AutoConfiguration.imports）文件里配置的自动配置类，再结合 @Conditional 系列条件注解做筛选，符合条件的才注册成 Bean。

拆开讲：

  1. @SpringBootApplication 是个组合注解，等于 @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan。
  2. @EnableAutoConfiguration 上又有 @Import(AutoConfigurationImportSelector.class)。
  3. AutoConfigurationImportSelector 实现 ImportSelector，selectImports() 方法返回要导入的配置类全限定名数组。
  4. 这些名字来自 SpringFactoriesLoader.loadFactoryNames()，扫描 classpath 下所有 META-INF/spring.factories 里的 EnableAutoConfiguration 键。
  5. 拿到候选配置类后，去重、排除（@EnableAutoConfiguration(exclude=...)），再用 @ConditionalOnClass、@ConditionalOnMissingBean 等条件注解过滤。
  6. 最后这些配置类被当成普通的 @Configuration 类解析，里面的 @Bean 方法注册成 Bean。

核心思想是「约定优于配置 + 条件装配」：类路径里有某个 jar 才生效，用户自己定义了 Bean 就退让。

完整解析

17MySQL 索引的底层原理是什么？为什么用 B+ 树？

面试现场

InnoDB 的索引底层是 B+ 树。

先说为什么不用别的：

  • 哈希索引：等值查询 O(1)，但不支持范围查询，也不支持排序（因为哈希值无序）。
  • 二叉树 / 红黑树：数据量大时树太高，一次查询要很多次磁盘 IO。
  • B 树：非叶子节点也存数据，导致一个节点能放的索引键更少，树更高；而且范围查询要在树里来回跳。
  • B+ 树：只有叶子节点存数据，非叶子节点只存索引键，所以一个节点能塞几百个键，树高通常只有 3~4 层，3 层就能存 2000 万行左右；叶子节点之间用双向链表连起来，范围查询和排序非常高效。

再说结构：

  • 聚簇索引（主键索引）：叶子节点存的是整行数据。
  • 二级索引（辅助索引）：叶子节点存的是主键值，需要回表再查一次聚簇索引。
  • 页大小 16KB，一个非叶子节点存「键 + 页号」，叶子节点存「数据行」。
完整解析

1）B+ 树的高度计算

假设一行数据 1KB，一个叶子页 16KB 能放 16 行。非叶子节点存「主键（bigint 8 字节）+ 页号（6 字节）= 14 字节」，加上页头开销按 16 字节算，一个非叶子页能放 16KB / 16B ≈ 1000 个指针。

  • 2 层：1000 × 16 = 1.6 万行
  • 3 层：1000 × 1000 × 16 = 1600 万行
  • 4 层：1600 亿行

所以主键用 bigint 而不是 varchar，能显著降低树高（短主键 → 一个节点放更多键）。这是「主键要短」的底层原因。

2）为什么非叶子节点不存数据是关键

B 树每个节点都要存「键 + 数据 + 指针」，一个页只能放几十个键，树高会到 5~6 层，多 2~3 次磁盘 IO。B+ 树把数据都压到叶子，非叶子纯粹当索引，这就是它 IO 次数少的原因。

3）聚簇索引和二级索引

聚簇索引（主键）：
  [非叶子: 10 | 20 | 30]
  [叶子: (10, 整行数据) → (20, 整行数据) → (30, 整行数据)]

二级索引（name）：
  [非叶子: 'a' | 'm' | 'z']
  [叶子: ('alice', 10) → ('bob', 20) → ('mike', 30)]
                              ↑ 只存主键值，要回表

回表：二级索引查到主键值后，再拿主键去聚簇索引查完整行。每回表一次就多一次 B+ 树查找，所以覆盖索引很重要。

4）为什么 InnoDB 必须有主键

因为聚簇索引就是按主键组织的，数据本身挂在主键 B+ 树上。

  • 有主键 → 用主键。
  • 没主键 → 找第一个非空唯一索引当主键。
  • 都没有 → 自动生成一个 6 字节的隐藏 row_id（全局共享，可能溢出）。

所以建表一定要显式指定主键，而且要自增。

5）为什么推荐自增主键

  • 自增主键：新数据总在 B+ 树最右边插入，顺序写，不会引起页分裂。
  • UUID 主键：随机插入，可能插到已有页的中间，导致页分裂（一个页拆成两个，还要移动数据），而且 UUID 32 字节太长，让树变高。

顺序写 vs 随机写，在机械硬盘上差几十倍。即使 SSD，页分裂带来的额外开销也很明显。

6）索引下推（ICP, Index Condition Pushdown）

MySQL 5.6 引入。联合索引 (name, age)，查询 WHERE name LIKE '张%' AND age = 20：

  • 没有 ICP：先用 name LIKE '张%' 从索引里找出所有主键，全部回表，回表后再过滤 age = 20。
  • 有 ICP：把 age = 20 下推到索引层过滤，只有满足条件的才回表。

效果：回表次数大幅减少。EXPLAIN 的 Extra 里显示 Using index condition。

7）最左前缀原则

联合索引 (a, b, c) 相当于建了 (a)、(a,b)、(a,b,c) 三个索引。

查询条件能否用索引用到哪些列
a = 1能a
a = 1 AND b = 2能a, b
a = 1 AND b = 2 AND c = 3能a, b, c
b = 2不能—
a = 1 AND c = 3能只用到 a（c 用不上，除非 ICP）
a > 1 AND b = 2能只用到 a（范围查询后面的列失效）

关键点：a 一旦用了范围查询（>、<、BETWEEN、LIKE '%x'），后面的列就无法用于索引定位（但可能用于 ICP 过滤）。

8）联合索引的列顺序怎么定

  • 等值查询的列放前面。
  • 区分度高的放前面（能过滤掉更多数据）。
  • 范围查询的列放最后。
  • 最实用的判断：看哪个列组合能让查询走最短的索引扫描路径。
追问预警
  • Q：为什么不用 B 树？
    A：B 树非叶子节点也存数据，导致每个节点能存的键少、树高更高、IO 更多；而且 B 树的叶子节点之间没有链表，范围查询要在树里来回跳。
  • Q：为什么不用跳表？
    A：跳表是内存结构（Redis 用），磁盘上不适合——跳表的节点分散，随机 IO 多；B+ 树一个节点就是一个 16KB 页，一次 IO 读一整页，最大化利用了磁盘的块读取特性。
  • Q：索引是不是越多越好？
    A：不是。① 每个索引都要占空间；② 写入时要维护所有索引，降低写性能；③ 优化器选择变多，可能选错索引。一般单表索引不超过 5 个。
  • Q：一张表能存多少数据？
    A：理论上受 B+ 树高度限制，3 层约 2000 万行。但实际瓶颈是索引的维护成本和查询性能，一般单表超过 500 万~1000 万行就考虑分库分表。

18你平时怎么做 SQL 索引优化？

面试现场

我的流程是：先定位慢 SQL → 再看执行计划 → 再改 SQL 或加索引 → 最后验证。

第一步，找慢 SQL：

  • 开慢查询日志 slow_query_log，设 long_query_time = 1。
  • 用 mysqldumpslow 或者 pt-query-digest 分析。
  • 生产上一般接监控（比如阿里云 DAS、SkyWalking）自动抓。

第二步，看执行计划 EXPLAIN，重点看几个字段：

  • type：访问类型，从好到坏是 system > const > eq_ref > ref > range > index > ALL。看到 ALL 就要警惕全表扫描。
  • key：实际用了哪个索引。如果是 NULL 就是没走索引。
  • rows：预估扫描行数，越小越好。
  • Extra：最关键。Using filesort（额外排序）、Using temporary（用了临时表）都是危险信号；Using index 是覆盖索引，最好。

第三步，常见的优化手段：

  1. 加合适的索引，尤其是联合索引。
  2. 避免索引失效：不要在索引列上做函数运算、类型隐式转换、LIKE '%xx' 前置通配。
  3. 用覆盖索引减少回表。
  4. 深分页优化。
  5. 大事务拆小、避免 SELECT *。
完整解析

1）索引失效的完整清单

场景例子原因
索引列上用函数WHERE DATE(create_time) = '2024-01-01'索引存的是原值，函数后无法用 B+ 树定位

2）深分页优化

-- 慢：扫描 100 万行，丢掉前 100 万行，只返回 10 行
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;

-- 方案一：游标分页（推荐，前提是 id 有序且连续查询）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;

-- 方案二：延迟关联（先走覆盖索引拿主键，再回表）
SELECT o.* FROM orders o
INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 10) t ON o.id = t.id;

-- 方案三：业务上限制翻页深度（比如只允许翻到 100 页）

方案二为什么快：子查询只查主键，走覆盖索引（不用回表），扫描的是索引页，IO 少得多；拿到 10 个主键后再回表，只回 10 次。

4）Using filesort 的优化

ORDER BY 用不上索引排序就会 filesort。

-- 索引 (a, b)
SELECT * FROM t WHERE a = 1 ORDER BY b;      -- 能用到索引排序，好
SELECT * FROM t WHERE a = 1 ORDER BY c;      -- 用不上，filesort
SELECT * FROM t WHERE a > 1 ORDER BY b;      -- 范围查询后 b 无序，filesort

优化思路：让 ORDER BY 的列和索引顺序一致，且前面的列都是等值查询。

5）其他实战经验

  • SELECT * 的危害：可能破坏覆盖索引；大字段（TEXT/BLOB）会被一起读出来，浪费网络和内存。
  • COUNT(*) 优化：InnoDB 不存行数，要扫索引。用最小的二级索引扫（COUNT(1) 或 COUNT(*) 优化器会选最小的索引）。超大表用计数器表或者 Redis 维护。
  • JOIN 优化：小表驱动大表；被驱动表的关联字段必须有索引（否则是 N 次全表扫描）；JOIN 字段类型必须一致。
  • 批量操作：用 INSERT INTO ... VALUES (...), (...), (...) 批量插入，比循环单条快很多；UPDATE 也尽量批量。
  • ORDER BY + LIMIT：能利用索引有序性时，找到前 N 条就停，不需要全排序。

6）怎么判断要不要加索引

-- 看列的区分度（基数），越接近 1 越好
SELECT COUNT(DISTINCT col) / COUNT(*) FROM table_name;

-- 区分度低于 0.1（比如性别、状态）基本不用单独建索引

但注意：区分度低不代表永远不建。如果某个状态值的数据量只占 0.1%（比如「待审核」），建索引反而很有用——因为索引能直接定位到这一小撮数据。关键是看「这个条件能过滤掉多少数据」。

追问预警
  • Q：EXPLAIN 里的 rows 准确吗？
    A：是估算值，基于统计信息（innodb_stats_persistent）。统计信息不准时优化器可能选错索引，可以 ANALYZE TABLE 更新统计信息。
  • Q：为什么有时候明明有索引却走了全表扫描？
    A：优化器算下来「走索引回表 + 随机 IO」比「全表顺序扫描」代价更高。比如 WHERE status = 1 命中了 90% 的数据，走索引要 90 万次随机回表，还不如全表扫。可以用 FORCE INDEX 强制，但要谨慎。
  • Q：怎么优化 COUNT(*)？
    A：① 用最小的二级索引；② 大表用 Redis 计数器或单独计数表；③ 如果只要「是否有数据」，用 LIMIT 1 代替 COUNT。
  • Q：in 和 exists 怎么选？
    A：IN 适合子查询结果集小的情况（先执行子查询）；EXISTS 适合子查询结果集大的情况（外层每行去子查询里找，找到就停）。MySQL 5.6 后有子查询优化，很多时候会自动转换，实际以 EXPLAIN 为准。

19讲一下 MySQL 的事务和隔离级别

面试现场

事务的四个特性 ACID：

  • 原子性（A）：要么全成功，要么全回滚。靠 undo log 实现。
  • 一致性（C）：数据从一个一致状态到另一个一致状态。这是目的，由 A、I、D 共同保证。
  • 隔离性（I）：并发事务互不干扰。靠锁 + MVCC 实现。
  • 持久性（D）：提交后永久生效。靠 redo log 实现。

四种隔离级别（从低到高）：

级别脏读不可重复读幻读
读未提交（RU）会会会
读已提交（RC）不会会会
可重复读（RR）不会不会InnoDB 基本解决
串行化（Serializable）不会不会不会

MySQL 默认是 RR（Oracle、PostgreSQL 默认 RC），这点要注意。

  • 脏读：读到了别的事务还没提交的数据。
  • 不可重复读：同一个事务里两次读同一行，结果不一样（别人改了并提交了）。
  • 幻读：同一个事务里两次范围查询，第二次多出了几行（别人插入了并提交了）。

RR 下 InnoDB 怎么解决幻读：快照读用 MVCC（读的是事务开始时的快照），当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）用间隙锁（Gap Lock）+ 临键锁（Next-Key Lock） 锁住范围，阻止别人插入。

完整解析

1）RR 到底有没有完全解决幻读？

严格来说没有完全解决，这是高频深挖点。

  • 快照读：RR 下第一次 SELECT 生成 Read View，后续都用这个 View，天然看不到别人新插入的数据，所以不会有幻读。
  • 当前读：用 Next-Key Lock 锁住范围，阻止插入，也不会有幻读。
  • 但有一种情况会幻读：
    事务 A：SELECT * FROM t WHERE id = 5;        -- 快照读，没这行
事务 B：INSERT INTO t VALUES (5, ...);        -- 提交
事务 A：UPDATE t SET name = 'x' WHERE id = 5; -- 当前读，更新成功（这条记录现在是 A 的事务版本了）
事务 A：SELECT * FROM t WHERE id = 5;         -- 快照读，能看到这行了！
    因为 UPDATE 是当前读，它读到了 B 插入的行并更新了它，之后 A 的快照读就能看到自己更新过的行了。

所以准确说法是：RR 通过 MVCC + Next-Key Lock 避免了大部分幻读，但在「快照读 + 当前读混合」的场景下仍可能出现。

2）间隙锁和临键锁

  • 记录锁（Record Lock）：锁住索引上的一条记录。
  • 间隙锁（Gap Lock）：锁住两个记录之间的「空隙」，防止插入。比如索引有 1、5，锁住 (1, 5) 这个区间，别人就插不进 3。
  • 临键锁（Next-Key Lock）：记录锁 + 间隙锁，锁住「左开右闭」区间 (1, 5]。RR 下默认加的就是临键锁。

关键点：

  • 间隙锁只在 RR 级别下存在，RC 级别没有（RC 下只有记录锁），所以 RC 的并发性能更好，这也是很多互联网公司把隔离级别改成 RC 的原因。
  • 间隙锁会互相冲突：两个事务可以同时持有同一个间隙的间隙锁（都是「阻止插入」的目的，不冲突），但都会阻塞插入。
  • 间隙锁容易死锁：因为锁的粒度大，两个事务可能互相等待。

3）为什么大厂把 RR 改成 RC

[mysqld]
transaction_isolation = READ-COMMITTED
  • 没有间隙锁，锁的范围小，并发性能更好，死锁概率低。
  • 配合 binlog 用 ROW 格式，主从复制也是安全的（RC 下 STATEMENT 格式会出问题）。
  • 业务上「不可重复读」的影响可以接受，或者用乐观锁/版本号解决。

注意：改 RC 的前提是 binlog_format = ROW，否则主从数据会不一致。

4）怎么选隔离级别

场景建议
互联网高并发业务RC + ROW binlog
金融、对账类RR 或 Serializable，一致性优先
报表、统计RR（避免同一事务内数据跳动）

5）事务的传播行为和失效场景（Spring 层面）

@Transactional 失效的常见原因：

  1. 方法不是 public（Spring AOP 代理限制）。
  2. 自调用：同类内部方法调用不走代理，注解失效。
  3. 异常被 catch 了没抛出（默认只对 RuntimeException 回滚）。
  4. 异常类型不是 RuntimeException（要配 rollbackFor = Exception.class）。
  5. 数据库引擎不支持事务（MyISAM）。
  6. 类没被 Spring 管理（自己 new 出来的对象）。

传播行为（Propagation）最常用的两个：

  • REQUIRED（默认）：有事务就加入，没有就新建。
  • REQUIRES_NEW：挂起当前事务，新开一个独立事务。用于「记录日志」这类「主业务回滚了但日志必须留下」的场景。
追问预警
  • Q：RR 和 RC 下 MVCC 有什么区别？
    A：核心区别是 Read View 的生成时机。RC 是每次 SELECT 都生成新的 Read View，所以能看到别人已提交的最新数据；RR 是只在第一次 SELECT 时生成，之后一直复用。详见下一题。
  • Q：什么是当前读和快照读？
    A：快照读是普通 SELECT，走 MVCC 读历史版本，不加锁；当前读是 SELECT ... LOCK IN SHARE MODE、FOR UPDATE、INSERT、UPDATE、DELETE，读的是最新版本，并且加锁。
  • Q：间隙锁会不会导致性能问题？
    A：会。间隙锁的冲突范围比记录锁大得多，RR 下高并发写入容易出现锁等待甚至死锁。所以「为什么大厂用 RC」的答案里，间隙锁是关键理由。

20讲一下 MVCC 的实现原理

面试现场

MVCC（多版本并发控制） 的核心是：读操作不加锁，通过读取历史版本实现并发读写不阻塞。

三个核心组件：

1）隐藏字段每行记录都有两个隐藏列：

  • DB_TRX_ID：最近修改这行的事务 ID。
  • DB_ROLL_PTR：回滚指针，指向 undo log 里的上一个版本。
  • （还有 DB_ROW_ID，没主键时用。）

2）undo log 版本链每次修改都会在 undo log 里生成一条记录，通过 DB_ROLL_PTR 串成链表。最新的在链表头，越老越往后。

3）Read View（读视图）事务做快照读时生成一个 Read View，里面有四个关键字段：

  • m_ids：当前活跃（未提交）的事务 ID 列表。
  • min_trx_id：m_ids 里的最小值。
  • max_trx_id：下一个要分配的事务 ID（不是 m_ids 的最大值）。
  • creator_trx_id：创建这个 Read View 的事务自己的 ID。

可见性判断：拿到某一版本的 DB_TRX_ID，按下面顺序判断：

  1. trx_id == creator_trx_id → 可见（自己改的，自己当然能看到）。
  2. trx_id < min_trx_id → 可见（这个事务在我开始之前就提交了）。
  3. trx_id >= max_trx_id → 不可见（这个事务在我生成 Read View 之后才开始的）。
  4. min_trx_id <= trx_id < max_trx_id → 看 trx_id 是否在 m_ids 里：
    • 在 m_ids 里 → 不可见（还活跃着，没提交）。
    • 不在 m_ids 里 → 可见（已经提交了）。

不可见就顺着 DB_ROLL_PTR 往下一个版本找，直到找到可见的版本或者链表结束。

RC 和 RR 的区别就在 Read View 的生成时机：RC 每次 SELECT 都生成，RR 只在第一次 SELECT 时生成一次。

完整解析

1）为什么 RR 只在第一次生成 Read View

因为要保证「可重复读」。如果每次查询都重新生成 View，就能看到别人新提交的数据了，那就变成 RC 了。

但要注意：RR 下的 Read View 是事务级别的，也就是同一个事务内所有快照读共用一个 View。

2）举个完整的例子

初始数据：id=1, name='张三', DB_TRX_ID=100（已提交）

事务 A（trx_id=200）：BEGIN
事务 B（trx_id=300）：BEGIN

① B 执行：UPDATE t SET name='李四' WHERE id=1;
   此时 undo log 链：
   [最新: name='李四', trx_id=300] --ROLL_PTR--> [旧: name='张三', trx_id=100]

② A 执行第一次 SELECT（生成 Read View）：
   m_ids = [200, 300]（A 自己 200 也活跃，B 300 活跃）
   min_trx_id = 200, max_trx_id = 301, creator_trx_id = 200
   判断最新版本 trx_id=300：
     300 >= max_trx_id(301)? 否
     200 <= 300 < 301 → 看是否在 m_ids 里 → 在 → 不可见
   顺着 ROLL_PTR 找上一版 trx_id=100：
     100 < min_trx_id(200) → 可见！
   所以 A 读到 '张三' ✅

③ B 提交：COMMIT

④ A 再执行 SELECT：
   RR 下复用 ② 的 Read View，判断逻辑完全一样 → 还是读到 '张三' ✅
   （这就是可重复读）

⑤ 如果是 RC：④ 会重新生成 Read View
   m_ids = [200]（B 已经提交，不在活跃列表了）
   max_trx_id = 301
   判断 trx_id=300：不在 m_ids 里 → 可见 → 读到 '李四'
   （这就是不可重复读）

3）undo log 什么时候能删

不是马上删。因为可能有别的事务还需要读老版本。InnoDB 用 Read View + purge 线程清理：

  • 如果某个版本已经没有任何活跃的 Read View 需要它了，就可以删。
  • 具体来说，当系统中最早的活跃事务都结束了，比它老的 undo 版本才能清理。
  • 所以长事务是 undo log 膨胀的元凶——一个跑了一小时的事务，会让这一小时内的所有 undo log 都不能清理，ibdata 或者 undo 表空间会暴涨。

这也是为什么生产上要严格限制事务时长。

4）MVCC 只能解决快照读

当前读（SELECT FOR UPDATE、UPDATE、DELETE）走的不是 MVCC，是加锁 + 读最新版本。所以：

  • 快照读 → MVCC → 无锁、高性能
  • 当前读 → 锁 → 保证读到最新数据

5）MVCC 的优缺点

优点缺点
读写不阻塞，并发高需要维护版本链，占用空间
读操作无锁，性能好长事务导致 undo 膨胀
实现了 RR 的「可重复读」实现复杂，需要 Read View 判断

6）版本链太长的问题

如果一个热点行被高频更新，版本链会很长，读操作要顺着链表一直找，性能下降。这时需要：

  • 控制事务时长，让 purge 及时清理。
  • 避免对同一行高频更新（可以考虑用计数器表 + 分片，把一行的更新分散到多行）。
追问预警
  • Q：max_trx_id 是 m_ids 的最大值吗？
    A：不是。是「下一个要分配的事务 ID」。所以 m_ids 里最大的可能是 max_trx_id - 1。这个细节很多人答错。
  • Q：Read View 是每行一个还是每个事务一个？
    A：每个事务一个（RR），或者每次查询一个（RC）。不是每行一个。所有行的可见性判断都基于同一个 Read View。
  • Q：为什么 MVCC 不能解决幻读？
    A：MVCC 只保证「读到的数据版本不变」，但不能阻止别的事务插入新行。新插入的行不在版本链上，快照读看不到（所以快照读没幻读），但当前读会看到，所以要靠间隙锁解决。
  • Q：undo log 和 redo log 的区别？
    A：undo log 是逻辑日志，记录「怎么回滚」，保证原子性 + MVCC；redo log 是物理日志，记录「在哪个页做了什么修改」，保证持久性。

21讲一下 MySQL 的三种日志（redo log、undo log、binlog）

面试现场

MySQL 有三种关键日志，作用完全不同：

日志层级类型作用
redo logInnoDB 引擎层物理日志（页级别）崩溃恢复，保证持久性 D
undo logInnoDB 引擎层逻辑日志事务回滚 + MVCC 快照，保证原子性 A
binlogMySQL Server 层逻辑日志（SQL/行）主从复制 + 数据恢复

核心是 WAL（Write-Ahead Logging）机制：修改数据时，先写 redo log，再改内存里的数据页，脏页由后台线程异步刷盘。这样即使宕机，也能用 redo log 恢复。

为什么要有 binlog 还要有 redo log？ 因为 redo log 是 InnoDB 特有的（MyISAM 没有），而且是循环写的、会被覆盖，不能用来做归档恢复；binlog 是 Server 层的、追加写、不会丢，可以用于主从复制和时间点恢复。

完整解析

1）redo log 的 WAL 机制

事务提交 → 写 redo log buffer → 刷到 redo log 文件（磁盘）→ 返回成功
（此时内存里的脏页还没落盘，后台线程慢慢刷）

好处：

  • 顺序写（redo log 是追加的）代替随机写（数据页刷盘是随机的），性能高很多。
  • 即使脏页还没刷盘就宕机，重启后也能从 redo log 恢复。

redo log 的结构：ib_logfile0、ib_logfile1，固定大小、循环写。有两个指针：

  • write pos：当前写到哪里。
  • check point：当前要擦除到哪里（这个位置之前的记录对应的脏页已经刷盘了）。
  • 两者之间就是可写空间，追上了就必须停下来刷脏页。

2）innodb_flush_log_at_trx_commit 参数（关键）

值行为安全性性能
1（默认）每次提交都 fsync 到磁盘不丢数据最差
0每秒 fsync 一次，提交时只写 buffer丢 1 秒最好
2每次提交写 OS cache，每秒 fsync丢 1 秒（OS 崩溃才丢）好

生产上一般用 1，除非是日志类、可容忍丢失的数据可以降到 2。

3）两阶段提交（2PC）

这是保证 redo log 和 binlog 一致的关键机制。为什么需要？因为这是两个独立的日志系统，如果只写一个就崩了，主从数据会不一致。

流程：

① 写 redo log，状态设为 prepare        ← 处于 prepare 状态
② 写 binlog
③ 提交事务，redo log 状态改为 commit

崩溃恢复的规则：

  • redo log 是 prepare 状态，binlog 完整 → 提交（因为 binlog 写了，从库能收到）。
  • redo log 是 prepare 状态，binlog 不完整 → 回滚。
  • redo log 已经是 commit 状态 → 提交。

为什么这个顺序能保证一致：

  • 先写 redo prepare 再写 binlog：如果写完 redo 就崩了，binlog 没写，回滚，主从一致。
  • 如果先写 binlog 再写 redo：binlog 写了但 redo 没写，主库回滚了，从库却执行了 binlog，主从不一致。

  • Q：redo log 会不会丢？
    A：innodb_flush_log_at_trx_commit = 1 时不会（事务提交就 fsync）；设为 0 或 2 时，宕机会丢最多 1 秒的数据。
  • Q：怎么恢复误删的数据？
    A：用 binlog + 全量备份做时间点恢复：mysqlbinlog --start-datetime --stop-datetime 找到误删前的 binlog，重放到误删前一刻，跳过误删的那条。前提是 binlog_format = ROW（能精确定位到具体行的操作）。

完整解析

1）synchronized 的锁升级过程

无锁 → 偏向锁 → 轻量级锁 → 重量级锁
        ↓ 有竞争     ↓ 竞争加剧
  • 偏向锁：只有一个线程访问时，把线程 ID 记在 Mark Word 里，后续同一线程进入不需要任何同步操作。适合「同一个线程反复进入同步块」的场景。
  • 轻量级锁：有第二个线程竞争时升级，用 CAS 自旋尝试获取，不阻塞。适合「锁持有时间短、竞争不激烈」。
  • 重量级锁：自旋失败或竞争激烈时升级，依赖操作系统的 mutex，线程会真正阻塞挂起（用户态 → 内核态切换，开销大）。

注意：JDK 15 之后偏向锁默认关闭了（-XX:-UseBiasedLocking），因为它的维护成本高、在现代应用里收益不明显（大量使用线程池，锁竞争场景变多）。JDK 18 之后相关参数被标记为废弃。

3）ReentrantLock 和 AQS

AQS（AbstractQueuedSynchronizer） 是 JUC 的核心框架，ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 都基于它。

AQS 内部维护：

  • 一个 volatile int state：表示同步状态。ReentrantLock 里 state = 0 表示未锁定，>0 表示重入次数。
  • 一个 CLH 双向队列：存放等待的线程。

加锁流程：

// 非公平锁
final void lock() {
    if (compareAndSetState(0, 1))         // 直接 CAS 抢，不管队列里有没有人等
        setExclusiveOwnerThread(Thread.currentThread());
    else
        acquire(1);                        // 抢不到，进队列
}

公平锁和非公平锁的区别：

// 公平锁的 tryAcquire 多了一个判断
if (!hasQueuedPredecessors() && compareAndSetState(0, acquires)) { ... }

hasQueuedPredecessors() 检查队列里有没有更早等待的线程，有就不能插队。

为什么非公平锁吞吐更高？ 因为避免了线程唤醒的延迟——队列头部的线程被唤醒需要时间（上下文切换），这期间新来的线程可以直接抢到锁干活，减少了 CPU 空转。

4）AQS 的共享模式和独占模式

  • 独占模式：ReentrantLock、ReentrantReadWriteLock 的写锁。同一时刻只有一个线程能持有。
  • 共享模式：Semaphore、CountDownLatch、ReentrantReadWriteLock 的读锁。多个线程可以同时持有。

5）synchronized 的原理（monitor）

synchronized (obj) {
    // 代码
}

编译后是：

monitorenter    ← 获取 monitor
// 代码
monitorexit     ← 释放 monitor（正常路径）
monitorexit     ← 释放 monitor（异常路径，编译器自动生成）

每个 Java 对象关联一个 monitor（管程），有 owner、entryList（等待获取锁的队列）、waitSet（调用 wait() 后进入的集合）。

wait() 和 sleep() 的区别（高频）：

  • wait() 释放锁，sleep() 不释放锁。
  • wait() 是 Object 方法，sleep() 是 Thread 静态方法。
  • wait() 必须在 synchronized 块里，sleep() 不需要。
  • wait() 可以被 notify() 唤醒，sleep() 只能等超时或被中断。
追问预警
  • Q：为什么 wait() 必须在 synchronized 块里？
    A：因为 wait() 要释放锁，前提是必须先持有锁。另外从设计上，wait/notify 是「条件等待」的语义，必须在临界区里才有意义，否则会有 lost wakeup（丢失唤醒）问题。
  • Q：synchronized 锁的是什么？
    A：修饰实例方法锁的是 this；修饰静态方法锁的是 Class 对象；修饰代码块锁的是括号里的对象。要注意锁对象必须是同一个才互斥——new 两个对象去锁，等于没锁。
  • Q：ReentrantLock 的 tryLock() 为什么能避免死锁？
    A：因为它可以指定超时时间，拿不到锁就返回 false 放弃，不会无限等待。死锁的四个必要条件之一是「循环等待」，超时打破了这个条件。
  • Q：什么是锁消除和锁粗化？
    A：锁消除是 JIT 通过逃逸分析发现锁对象不会逃逸出方法，直接去掉锁（比如 StringBuffer 在局部变量里）。锁粗化是把循环内反复加解锁的操作合并成一次大的加解锁，减少开销。

23ThreadLocal 的原理？为什么会有内存泄漏？

面试现场

原理：每个 Thread 内部都有一个 ThreadLocalMap 字段（注意是在 Thread 里，不是在 ThreadLocal 里）。ThreadLocalMap 的 key 是 ThreadLocal 对象的弱引用，value 是强引用。

set(value) 就是往当前线程的 ThreadLocalMap 里放一个 (this, value) 的 Entry；get() 就是拿 this 去查。

内存泄漏的原因：

  • key 是弱引用，当外部的 ThreadLocal 对象被 GC 回收后，Entry 的 key 变成 null，但 value 还是强引用。
  • 如果这个线程一直活着（比如线程池里的核心线程），这个 value 就永远无法回收 → 内存泄漏。

解决办法：用完必须 remove()，放在 finally 里。

为什么 key 用弱引用而不是强引用？ 这是一个权衡：如果用强引用，ThreadLocal 对象和 value 就绑在一起了，ThreadLocal 永远被 ThreadLocalMap 引用，更没法回收。用弱引用至少让 key 能被回收，value 通过 get/set/remove 时的探测式清理有机会被清掉。但最终还是得靠手动 remove()。

完整解析

1）数据结构

// Thread 里
ThreadLocal.ThreadLocalMap threadLocals = null;

// ThreadLocalMap 里
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;                        // 强引用！
    Entry(ThreadLocal<?> k, Object v) {
        super(k);                        // key 是弱引用
        value = v;
    }
}

// ThreadLocal 里
public void set(T value) {
    Thread t = Thread.currentThread();
    ThreadLocalMap map = getMap(t);      // 拿当前线程的 map
    if (map != null) map.set(this, value);
    else createMap(t, value);
}

关键点：ThreadLocal 本身不存数据，它只是个「key 的封装」。数据存在线程自己的 map 里。这也是为什么说 ThreadLocal 能实现「线程隔离」——每个线程有自己独立的 map。

2）引用关系图

Thread（线程池里的核心线程，长期存活）
  └─ ThreadLocalMap
       └─ Entry
            ├─ key:  弱引用 ──→ ThreadLocal 对象   ← 可能被 GC 回收，变成 null
            └─ value: 强引用 ──→ 实际数据           ← 永远无法回收！

3）探测式清理（expungeStaleEntry）

ThreadLocalMap 用的是开放地址法（线性探测）解决哈希冲突，不是链表。每次 get/set/remove 时，如果遇到 key 为 null 的 Entry，会顺手把它清掉，并把后面冲突的元素重新定位。

所以即使不手动 remove，只要后续还有操作，也有机会被清理——但这是碰运气，不能依赖。

4）为什么哈希是 HASH_INCREMENT = 0x61c88647

private static final int HASH_INCREMENT = 0x61c88647;
private final int threadLocalHashCode = nextHashCode();

0x61c88647 是斐波那契散列的黄金分割数，用它做递增能让 ThreadLocal 的哈希值均匀分布在 2 的幂长度的数组里，减少冲突。

5）remove() 做了什么

private void remove(ThreadLocal<?> key) {
    Entry[] tab = table;
    int i = key.threadLocalHashCode & (len - 1);
    for (Entry e = tab[i]; e != null; e = tab[i = nextIndex(i, len)]) {
        if (e.get() == key) {
            e.clear();                        // 断开弱引用
            expungeStaleEntry(i);             // 清空 value 并整理
            return;
        }
    }
}

注意 e.clear() 后，expungeStaleEntry 会把 value 置为 null，这样 value 才能真正被 GC 回收。

6）InheritableThreadLocal 和 TransmittableThreadLocal

  • InheritableThreadLocal：子线程可以继承父线程的 ThreadLocal 值。原理是 Thread 初始化时把父线程的 inheritableThreadLocals 复制过来。
  • 问题：线程池场景下失效！因为线程池的线程是复用的，创建一次就固定了，不会每次提交任务都新建线程，所以继承不到。
  • TransmittableThreadLocal（TTL，阿里开源）：解决线程池场景的传递问题。通过装饰线程池（TtlExecutors.getTtlExecutorService）在任务提交时捕获快照，任务执行时回放，执行完恢复。

// 错误：忘记 remove，线程池场景必然泄漏

    // ... 业务逻辑，如果抛异常就永远不会 remove

}

还有更隐蔽的坑：如果没有 remove，下一个复用这个线程的任务会读到上一个任务的用户信息 —— 这不仅是内存泄漏，更是数据串号的安全事故。

追问预警
  • Q：key 用弱引用，value 为什么不用弱引用？
    A：如果 value 也用弱引用，那么任何一次 GC 都可能把数据清掉，业务拿不到值，ThreadLocal 就没法用了。所以 value 必须强引用，代价就是要手动 remove。
  • Q：ThreadLocalMap 和 HashMap 的区别？
    A：① 冲突解决：ThreadLocalMap 用开放地址法，HashMap 用链地址法（链表+红黑树）；② key 类型：ThreadLocalMap 的 key 是弱引用的 ThreadLocal，HashMap 是强引用；③ 清理机制：ThreadLocalMap 有探测式清理；④ ThreadLocalMap 没有实现 Map 接口，是专门定制的。
  • Q：父子线程怎么传递 ThreadLocal？
    A：用 InheritableThreadLocal，但线程池场景要用 TransmittableThreadLocal。
  • Q：为什么说 ThreadLocal 不是用来解决线程安全问题的？
    A：严格来说它不是「解决」而是「规避」。它的思路是「每个线程一份副本，互不共享」，从根上避免了共享，而不是通过同步去协调共享。这是理解上的关键区别。

24线程池的核心参数有哪些？怎么设置？

面试现场

ThreadPoolExecutor 有七个参数：

  1. corePoolSize：核心线程数，即使空闲也不会被回收（除非开了 allowCoreThreadTimeOut）。
  2. maximumPoolSize：最大线程数。
  3. keepAliveTime：非核心线程空闲后的存活时间。
  4. unit：时间单位。
  5. workQueue：任务队列。
  6. threadFactory：线程工厂，一般用来给线程起有意义的名字，方便排查问题。
  7. handler：拒绝策略。

执行流程（必须背下来）：

提交任务
  ↓
① 核心线程数没满？ → 创建核心线程执行
  ↓ 满了
② 任务队列没满？ → 放进队列排队
  ↓ 满了
③ 线程数没到 maximum？ → 创建非核心线程执行
  ↓ 满了
④ 执行拒绝策略

关键点：是先入队，队列满了才扩容线程，不是先扩容。这个顺序很多人答错，也是「为什么用无界队列会导致 maximumPoolSize 失效」的原因。

拒绝策略有四种：

  • AbortPolicy（默认）：抛 RejectedExecutionException。
  • CallerRunsPolicy：由提交任务的线程自己执行，能起到反压作用，不丢任务。
  • DiscardPolicy：直接丢弃，不报错。
  • DiscardOldestPolicy：丢掉队列里最老的任务，再提交当前任务。
完整解析

1）为什么先入队再扩容？

这是 Doug Lea 的设计取舍：希望用最少的线程处理尽可能多的任务。因为创建线程是有成本的（栈内存 1MB、上下文切换），能排队就不急着开新线程。

副作用：如果用 LinkedBlockingQueue（默认容量 Integer.MAX_VALUE，等于无界），队列永远不会满，maximumPoolSize 就永远用不上，线程数会一直停在 corePoolSize。这是最经典的线程池坑。

2）队列的选择

队列特点风险
ArrayBlockingQueue有界，数组实现推荐，容量要合理
LinkedBlockingQueue默认无界（Integer.MAX_VALUE）OOM 风险，maximumPoolSize 失效

结论：生产上必须用有界队列。阿里巴巴 Java 开发手册明确规定：「线程池不允许使用 Executors 去创建，应通过 ThreadPoolExecutor 的方式，明确指定参数」。

4）线程数怎么定

经典公式（只能当起点，必须压测）：

  • CPU 密集型（大量计算）：N + 1。多一个线程是为了在偶发的缺页中断等暂停时顶上。
  • IO 密集型（大量网络/磁盘等待）：2N 或者 N / (1 - 阻塞系数)。阻塞系数一般在 0.8~0.9，所以大约是 N × 5~10。

更工程化的算法（美团那篇《Java 线程池实现原理及其在美团业务中的实践》里的）：

线程数 = CPU 核数 × 目标 CPU 利用率 × (1 + 等待时间 / 计算时间)

但真正的答案是：先按公式给个初值，然后压测，看 CPU 利用率、GC、响应时间、队列积压情况，再调。

6）动态调参

ThreadPoolExecutor 提供了 setCorePoolSize、setMaximumPoolSize 方法，可以运行时调整。

美团开源的方案是：把线程池参数放配置中心，监听变更事件动态 set。注意 setMaximumPoolSize 调小时，只影响后续，不会中断正在执行的任务；而且如果当前线程数大于新的 corePoolSize，多出来的线程会被回收。

自己实现一个动态线程池的要点：

  • 用 setCorePoolSize / setMaximumPoolSize 动态调整。
  • 队列容量不能动态改（ArrayBlockingQueue 的 capacity 是 final 的），要动态改得自己实现一个可变的 BlockingQueue（重写 offer，用 volatile 控制容量）。
  • 注册到配置中心的监听器上。

7）线程池隔离

不要让所有业务共用一个线程池。一个业务把线程池打满，会拖垮所有业务（故障扩散）。

  • 按业务维度拆：订单线程池、支付线程池、通知线程池。
  • 按重要性拆：核心业务和非核心业务分开。
  • 按依赖拆：调 A 服务的、调 B 服务的分开（防止某个下游变慢拖垮所有调用）。

8）shutdown 和 shutdownNow

  • shutdown()：不再接收新任务，等待已提交的任务（包括队列里的）执行完。
  • shutdownNow()：不再接收新任务，尝试中断正在执行的任务，返回队列里未执行的任务列表。

优雅关闭：先 shutdown()，然后 awaitTermination(timeout) 等待，超时了再 shutdownNow()。

追问预警
  • Q：核心线程会被回收吗？
    A：默认不会。设置 allowCoreThreadTimeOut(true) 后，核心线程空闲超过 keepAliveTime 也会被回收。
  • Q：线程池里的线程抛异常了会怎样？
    A：任务被丢弃，线程不会销毁，线程池会创建一个新线程补上。但如果 execute 提交的任务抛了未捕获异常，异常会被吞掉（因为 runWorker 里 catch 了），所以要么在任务内部 try-catch，要么设置 UncaughtExceptionHandler，要么用 submit + Future.get() 拿到异常。
  • Q：submit 和 execute 的区别？
    A：execute 只能提交 Runnable，异常直接抛出；submit 可以提交 Runnable/Callable，返回 Future，异常被包装在 Future 里，不调用 get() 就永远看不到异常——这是「任务静默失败」的常见原因。
  • Q：怎么判断线程池任务都执行完了？
    A：① Future.get() 逐个等；② CountDownLatch；③ invokeAll 返回 Future 列表；④ 自己维护计数器。
  • Q：线程池的线程复用了，ThreadLocal 会不会串号？
    A：会！这是线程池 + ThreadLocal 的经典坑，任务结束时必须 remove()，否则下一个任务会读到上一个任务的数据。

RocketMQ

25RocketMQ 的整体架构是怎么样的？

面试现场

RocketMQ 有四个核心角色：NameServer、Broker、Producer、Consumer。

  • NameServer：注册中心，无状态、节点之间不通信。负责 Broker 的注册和路由信息的维护。Producer 和 Consumer 从它这里拿路由。
  • Broker：消息存储和转发的核心。分 Master 和 Slave，Master 负责读写，Slave 做数据备份（同步或异步复制）。消息存在 CommitLog 里。
  • Producer：消息生产者。支持集群部署，同一个 Producer Group 里的实例可以往多个 Broker 发。
  • Consumer：消息消费者。有集群消费（一条消息只被组内一个消费者消费）和广播消费（每个消费者都收到）两种模式。

核心的存储结构：

  • CommitLog：所有消息顺序写进去，这是 RocketMQ 高性能的关键。
  • ConsumeQueue：每个 Topic 的每个队列一个，存的是「消息在 CommitLog 里的物理偏移量 + 消息大小 + tag 的 hash」，相当于索引。
  • IndexFile：按消息 key 或时间查询用的索引。

消息流向：Producer → Broker（CommitLog 顺序写）→ Consumer（先读 ConsumeQueue 定位，再读 CommitLog 拿消息）。

完整解析

1）为什么 NameServer 无状态、节点间不通信？

这是 RocketMQ 相比 Kafka（依赖 ZooKeeper）的一个优势：

  • 部署简单：多个 NameServer 互不通信，各存各的路由，随便加机器。
  • 没有脑裂问题：因为不需要选主、不需要数据同步。
  • 可用性高：挂掉几台没关系，只要还有一台活着，Producer/Consumer 就能拿到路由。
  • 代价：路由信息有短暂的不一致（各个 NameServer 感知 Broker 上下线有时间差），但因为 Producer/Consumer 会定时拉取（默认 30 秒）并且本地缓存，这点延迟可以接受。

2）Broker 的 Master/Slave

模式说明特点
同步双写（SYNC_MASTER）消息写主成功 + 写从成功才返回可靠性高，性能略低
异步复制（ASYNC_MASTER）写主成功就返回，异步同步给从性能高，主挂了可能丢数据
DLedger 模式基于 Raft 自动选主主挂了能自动切换，不需要人工介入

注意：普通 Master/Slave 模式下，Master 挂了 Slave 不能自动切换成 Master（老版本），需要人工介入或者用 DLedger。这是 RocketMQ 4.x 的一个痛点，5.0 引入了 Controller 模式（基于 Raft）来自动主从切换。

3）CommitLog 的设计精髓

所有 Topic 的消息都写到同一个 CommitLog 文件里（这一点和 Kafka 完全不同——Kafka 是每个 Partition 一个文件）。

优点：

  • 完全的顺序写，磁盘顺序写速度接近内存随机写，这是 RocketMQ 高吞吐的根本原因。
  • 文件大小固定 1GB，写满就新建一个，方便内存映射和清理。

缺点：

  • ConsumeQueue 需要额外维护（写消息时要同步更新 ConsumeQueue）。
  • 单机 CommitLog 写入是串行的（虽然有锁优化）。

CommitLog 文件结构：{topic}/{queueId}/{offset}，每个文件 1GB，默认保留 72 小时（fileReservedTime）。

4）ConsumeQueue 的作用

如果没有 ConsumeQueue，消费者要按 Topic 找消息就得遍历整个 CommitLog（因为不同 Topic 的消息混在一起）。

ConsumeQueue 相当于一个稀疏索引，每个条目 20 字节：

[CommitLog 物理偏移量(8字节)] [消息长度(4字节)] [tag hashcode(8字节)]

消费者先读 ConsumeQueue（顺序读，很小，能全部加载到内存），拿到偏移量再去 CommitLog 读真正的消息。典型的「空间换时间 + 两级索引」设计。

5）Producer 的发送方式

方式说明
同步发送发完等 Broker 响应，可靠性高，RT 高
异步发送发完不等，回调处理结果，吞吐高
单向发送（Oneway）发完不管，用于日志采集等可丢失场景

6）Consumer 的消费模式

  • 集群消费（Clustering）：同一个 Consumer Group 里的消费者分摊队列，一条消息只被一个消费者消费。最常用。
  • 广播消费（Broadcasting）：每个消费者都收到全量消息。

Push 和 Pull：RocketMQ 的 PushConsumer 底层其实是长轮询的 Pull（PullConsumer 是用户自己控制拉取）。长轮询的好处是：有新消息立刻返回，没消息就挂起一段时间（默认 15 秒），兼顾实时性和性能。

7）Topic 和 Queue

  • 一个 Topic 可以配置多个 Queue（默认 4 个）。
  • Queue 是并行消费的最小单位：一个 Queue 同一时刻只能被一个消费者消费（集群模式下）。
  • 所以消费者数量超过 Queue 数量时，多出来的消费者分不到队列，会空转——这是扩容消费者时的关键限制。
追问预警
  • Q：RocketMQ 为什么不用 ZooKeeper？
    A：ZooKeeper 的写是强一致的（ZAB 协议），写入有瓶颈，而且引入 ZK 会让部署和运维复杂。NameServer 无状态设计更轻量、更简单，虽然牺牲了一点一致性（路由有延迟），但对消息场景够用。
  • Q：Broker 是怎么做高可用的？
    A：主从复制（同步/异步）+ DLedger/Controller 自动选主。生产上如果是金融类场景，建议用 DLedger 模式。
  • Q：CommitLog 单文件 1GB 会不会太大？
    A：1GB 是经过权衡的：太小会导致文件数量多、频繁切换；太大则内存映射（mmap）的效率下降。而且 RocketMQ 用 mmap（内存映射） 读写 CommitLog，1GB 正好适合。
  • Q：消息存在磁盘上，为什么还这么快？
    A：① 顺序写（CommitLog 追加）；② mmap 内存映射（写的是页缓存，由 OS 异步刷盘）；③ 零拷贝（mmap + write 或者 sendfile）在消费时减少数据拷贝。

26RocketMQ 如何保证消息的顺序性？

面试现场

先明确一个前提：RocketMQ 只能保证「同一个队列（MessageQueue）内的消息是严格有序的」，跨队列不保证。

所以要分两种情况：

1）全局有序一个 Topic 只配一个 Queue，Producer 单线程发送，Consumer 单线程消费。这样能保证全局有序，但吞吐量极低，几乎没人这么用。

2）分区有序（局部有序）—— 这才是生产上的做法关键是把需要保序的消息发到同一个队列，然后在消费端串行消费这个队列。

具体做法：

发送端：用 MessageQueueSelector，按业务 key（比如订单号）选择队列：

producer.send(msg, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        String orderId = (String) arg;
        int index = Math.abs(orderId.hashCode()) % mqs.size();
        return mqs.get(index);          // 同一个订单号永远进同一个队列
    }
}, orderId);

消费端：用 MessageListenerOrderly（顺序消费），它会给队列加锁：

consumer.registerMessageListener(new MessageListenerOrderly() {
    @Override
    public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, ConsumeOrderlyContext context) {
        // 处理业务，同一个队列串行执行
        return ConsumeOrderlyStatus.SUCCESS;
    }
});

和 MessageListenerConcurrently 的区别：

  • Concurrently：多线程并行消费，不保证顺序。
  • Orderly：对队列加锁，同一队列同一时刻只有一个线程消费，保证顺序。而且本地队列缓存保证同一队列的消息是顺序处理的。
完整解析

1）消费端是怎么加锁的

MessageListenerOrderly 的锁分三层：

  • Broker 端：ConsumerManager 里对 MessageQueue 加分布式锁（RebalanceImpl.lock()），保证一个队列同一时刻只被一个消费者实例消费。
  • 客户端：ConsumeMessageOrderlyService 里对每个 MessageQueue 有一个 Object lockObj，用 synchronized 保证同一队列在客户端内串行。
  • 本地队列：维护一个 ProcessQueue，同一队列的消息顺序处理。

所以顺序消费的性能瓶颈就在这里——同一个队列是串行的。

2）顺序消费的失败处理（重要）

顺序消费下，如果某条消息消费失败：

  • 返回 SUSPEND_CURRENT_QUEUE_A_MOMENT，当前队列暂停一会儿再重试（默认从 10ms 开始，每次翻倍，最大 30s）。
  • 不能跳过！因为跳过就破坏了顺序。
  • 这样会导致这个队列被阻塞——如果某条消息一直失败，整个队列就卡死了。

所以顺序消费必须保证「消费逻辑不会因为某条坏消息而永久失败」：

  • 消费逻辑要做幂等和容错。
  • 对于确定无法处理的消息，要有降级机制（比如记录到异常表，然后返回 SUCCESS 跳过），否则会阻塞整个队列。

3）为什么会出现乱序

即使发送端保证了顺序，也可能乱序：

环节乱序原因
发送端多线程并发发送、异步发送重试（重试可能排到后面）
Broker同一队列内不会乱序（顺序写）
消费端多线程并行消费、重试消息被放到重试队列后重新投递
网络重试消息延迟到达

所以「发送有序 + 存储有序 + 消费有序」三者缺一不可。

4）消费端的另一个坑：消费重试导致的乱序

即使使用 MessageListenerOrderly，如果消息进入重试队列，重试消息可能会被投递到其他队列（默认重试队列是 %RETRY%{ConsumerGroup}，并且队列数和原队列数一致，所以还是能保证同队列重试）。

但要注意重试队列的 Queue 数量要和原 Topic 一致，否则会乱序。

5）实际业务里怎么用

以订单状态流转为例（创建 → 支付 → 发货 → 完成）：

  • 用 orderId 作为分片 key，保证同一订单的消息进同一队列。
  • 消费端用 MessageListenerOrderly 串行消费。
  • 消费逻辑里做状态机校验（比如「已支付」状态不能直接跳到「已完成」），这是最后的兜底——即使顺序真的乱了，状态机也能拦住非法流转。

状态机校验这一层很重要，因为完全依赖 MQ 保证顺序是有风险的，业务层要有兜底。

6）顺序消息 vs 普通消息的性能对比

维度普通消息顺序消息
发送可以多线程并发建议单线程（同队列）
消费多线程并行单队列串行
吞吐高低（受单队列限制）
可靠性高低（一个卡住全队等）

所以只在真正需要保序的场景用（订单状态、资金流水），其他场景用普通消息 + 业务幂等。

追问预警
  • Q：怎么提高顺序消息的吞吐？
    A：按业务维度分片。比如订单用 orderId % N 分到 N 个队列，不同订单可以并行，同一订单串行。这样吞吐提升了 N 倍，同时保住了「同一业务实体的顺序」。
  • Q：顺序消息消费失败会不会阻塞其他队列？
    A：不会。只阻塞当前队列，其他队列正常消费。但如果你的消费者实例只负责一个队列，那就等于全阻塞了。
  • Q：RocketMQ 的顺序消息能保证 Exactly Once 吗？
    A：不能。顺序消费也可能重复（比如消费成功但 ACK 丢失，会重投），必须业务幂等。

27RocketMQ 事务消息的核心机制是什么？

面试现场

要解决的问题：本地事务和发消息这两个操作，怎么保证原子性？

经典场景是「订单创建成功后，发消息通知库存扣减」。如果先扣库存再发消息，发消息失败就漏了；如果先发消息再扣库存，扣库存失败就多扣了。

RocketMQ 的解法是「两阶段提交 + 事务回查」：

第一阶段：发半消息（Half Message）

  1. Producer 向 Broker 发送一条半消息。
  2. 半消息对消费者不可见，存在特殊的 Topic（RMQ_SYS_TRANS_HALF_TOPIC）里。
  3. Broker 返回发送成功。

第二阶段：执行本地事务

  1. Producer 收到半消息成功响应后，执行本地事务（比如写订单表）。
  2. 根据本地事务结果，向 Broker 发送 Commit 或 Rollback。
    • Commit：消息从半消息 Topic 转成真正的消息，消费者可见。
    • Rollback：删除半消息，消费者永远看不到。

兜底：事务回查

  1. 如果 Broker 长时间没收到 Commit/Rollback（Producer 挂了、网络断了），Broker 会定时回查（默认 60 秒后开始，最多 15 次）Producer。
  2. Producer 实现 checkLocalTransaction，查本地事务表判断事务到底成功没有，再返回 Commit 或 Rollback。

核心思想：用「回查」这个机制，把「不确定」变成「可确定」。因为本地事务的结果一定能从数据库里查出来。

完整解析

1）代码实现（核心两个方法）

public class OrderTransactionListener implements TransactionListener {

    // 执行本地事务
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            // 写订单表
            orderService.createOrder(order);
            return LocalTransactionState.COMMIT_MESSAGE;      // 成功，提交消息
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;    // 失败，回滚消息
        }
        // 注意：返回 UNKNOW 表示不确定，Broker 会回查
    }

    // 事务回查：Broker 长时间没收到结果时调用
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        String orderId = msg.getKeys();
        // 查数据库，看订单到底建没建成功
        Order order = orderService.getByOrderId(orderId);
        if (order != null) {
            return LocalTransactionState.COMMIT_MESSAGE;
        }
        return LocalTransactionState.ROLLBACK_MESSAGE;
    }
}

// 发送事务消息
TransactionMQProducer producer = new TransactionMQProducer("order_group");
producer.setTransactionListener(new OrderTransactionListener());
producer.setExecutorService(executorService);   // 回查线程池
producer.start();

producer.sendMessageInTransaction(msg, null);

关键点：

  • 回查时不能依赖内存状态（因为 Producer 可能重启了），必须查数据库。
  • 所以业务上需要一张事务状态表（或者直接查业务表），记录每条消息对应的本地事务结果。

2）半消息是怎么实现的

半消息不是真的「另一条消息」，而是把消息的 Topic 替换成 RMQ_SYS_TRANS_HALF_TOPIC，同时备份原始 Topic 和 QueueId到消息属性里。

  • 半消息写入 CommitLog，但ConsumeQueue 是写到半消息 Topic 下的，所以普通消费者读不到。
  • Commit 时：把消息重新写入 CommitLog（Topic 恢复成原 Topic），这样消费者就能读到了。注意这是「再写一次」，不是「改状态」——因为 CommitLog 是 append-only 的。
  • Rollback 时：只写一个 OP 消息到 RMQ_SYS_TRANS_OP_HALF_TOPIC，标记这条半消息已经被处理（回滚）了，不再回查。

3）回查机制的具体参数

参数默认值说明
transactionTimeOut6s半消息的过期时间
transactionCheckMax15最大回查次数
transactionCheckInterval60s回查间隔

超过最大回查次数后，消息会被丢弃并打印错误日志。所以业务要监控这个日志。

4）事务消息的三种状态

  • COMMIT_MESSAGE：提交，消费者可见。
  • ROLLBACK_MESSAGE：回滚，消费者不可见。
  • UNKNOW：未知，等 Broker 回查。

5）事务消息的局限（面试加分点）

  1. 不保证本地事务和消息的强一致，只保证最终一致。因为回查间隔是 60 秒，这期间消息是不可见的，业务上是「延迟可见」。
  2. 回查最多 15 次，之后消息会被丢弃。所以回查逻辑必须能覆盖所有情况（能明确判断成功或失败），不能一直返回 UNKNOW。
  3. 半消息不能保证 100% 不丢（极端情况下 Broker 数据丢失）。
  4. 事务消息不支持延迟消息、批量发送。
  5. 回查是「反查」语义，业务必须提供可查询的落地状态。

6）事务消息 vs 本地消息表

方案优点缺点
RocketMQ 事务消息框架层解决，业务侵入小依赖 MQ 特性，回查有延迟
本地消息表不依赖 MQ 特性，通用需要额外的表 + 定时任务补偿，代码侵入大
最大努力通知简单不保证一致，靠对账兜底

本地消息表的思路：在同一个本地事务里，同时写业务表和消息表（都是本地事务，天然原子），然后由定时任务扫描消息表把消息发出去，发成功就标记。不依赖 MQ 的任何特性，Kafka 也能用。

7）实际项目怎么选

  • 用的是 RocketMQ，且业务能接受几十秒延迟 → 事务消息。
  • 用的不是 RocketMQ，或者需要更强的可控性 → 本地消息表。
  • 要求绝对可靠、可对账 → 本地消息表 + 定时对账。
追问预警
  • Q：为什么半消息对消费者不可见？
    A：因为半消息的 ConsumeQueue 写在 RMQ_SYS_TRANS_HALF_TOPIC 下，消费者只订阅自己关心的 Topic，读不到这个系统 Topic。
  • Q：Commit 的时候是修改消息状态吗？
    A：不是。CommitLog 是 append-only 的，不能修改。Commit 的实际操作是把消息重新写一遍到原 Topic，然后在半消息 Topic 里写一个 OP 消息标记「已提交」。
  • Q：如果回查时数据库也查不到，怎么办？
    A：返回 ROLLBACK_MESSAGE（回滚）。因为查不到说明本地事务没成功，消息也不该发出去。但要注意回查和本地事务执行可能有时间差（比如本地事务还在进行中），所以业务上要么让本地事务快速结束，要么用「事务状态表」明确记录「处理中」状态。
  • Q：事务消息能保证消息不重复吗？
    A：不能。回查时可能 Producer 已经 Commit 过了但 Broker 没收到，回查会再 Commit 一次（实际是幂等的，因为 OP 消息有去重）。但消费端仍可能重复消费，业务必须幂等。

28RocketMQ 如何保证消息不丢失？

面试现场

消息从生产到消费要经过三个阶段，每个阶段都可能丢，必须逐段防护。

一、生产阶段（Producer → Broker）

  • 用同步发送（send）而不是异步或单向发送，确保收到 Broker 的 ACK。
  • 开启失败重试：producer.setRetryTimesWhenSendFailed(3)，同步发送默认重试 2 次。
  • 关键业务用事务消息，确保本地事务和消息的原子性。

二、存储阶段（Broker 落盘）

  • 刷盘方式用同步刷盘：flushDiskType = SYNC_FLUSH。异步刷盘（默认 ASYNC_FLUSH）在 Broker 宕机时会丢页缓存里的消息。
  • 主从复制用同步双写：brokerRole = SYNC_MASTER。异步复制（默认 ASYNC_MASTER）下 Master 挂了会丢没同步过去的数据。
  • 多副本 + DLedger：基于 Raft 保证多数派写入成功才返回，可靠性最高。

三、消费阶段（Broker → Consumer）

  • 消费成功后才返回 CONSUME_SUCCESS，失败返回 RECONSUME_LATER。
  • 消费逻辑必须先把业务处理完再 ACK，不能先 ACK 再处理。
  • 失败自动重试：默认重试 16 次，每次间隔递增（1s, 5s, 10s, 30s, 1m, 2m, ...），超过后进入死信队列（%DLQ%{ConsumerGroup}）。
  • 死信队列必须有人工处理或者告警，否则消息就真的丢了。

一句话总结：同步发送 + 同步刷盘 + 同步双写 + 消费成功再 ACK + 死信队列告警，这五条都做到才叫「不丢」。

完整解析

1）各阶段丢失场景汇总

阶段丢失场景防护措施
Producer发送失败没重试；异步发送回调没处理同步发送 + 重试 + 事务消息
Broker（内存）Broker 宕机，页缓存里的消息没刷盘同步刷盘 SYNC_FLUSH
Broker（磁盘）磁盘损坏主从 + RAID + 多副本
Broker（主从）Master 挂了，Slave 还没同步到同步双写 SYNC_MASTER / DLedger
Consumer先 ACK 再处理业务，处理失败消息已 ACK先处理再 ACK
Consumer消费失败没重试机制返回 RECONSUME_LATER + 死信队列

2）刷盘方式的取舍

方式行为可靠性性能
ASYNC_FLUSH（默认）消息写页缓存就返回，后台定时刷盘宕机丢 1~2 秒数据高
SYNC_FLUSH每条消息都等 fsync 完成才返回不丢低（吞吐降一个数量级）

生产建议：性能敏感且能容忍少量丢失的场景用异步刷盘 + 同步双写（因为主从同步能兜住单机宕机）；金融级场景用同步刷盘。

3）主从复制的取舍

模式行为丢失风险
ASYNC_MASTER（默认）Master 写成功就返回Master 宕机且数据没同步 → 丢
SYNC_MASTERMaster + Slave 都写成功才返回不丢（除非两个都挂）

注意一个经典坑：SYNC_MASTER 下，如果 Slave 挂了或者同步很慢，Master 会阻塞等待，可能导致发送超时。所以 Slave 的健康监控很重要。

4）消费端的正确姿势

consumer.registerMessageListener((MessageListenerConcurrently) (msgs, context) -> {
    for (MessageExt msg : msgs) {
        try {
            // 1. 先执行业务（写库等）
            businessService.handle(msg);
        } catch (Exception e) {
            log.error("消费失败，等待重试", e);
            // 2. 失败就返回重试，不要吞掉异常返回 SUCCESS
            return ConsumeConcurrentlyStatus.RECONSUME_LATER;
        }
    }
    // 3. 全部成功才 ACK
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});

两个反例：

  • 先 ACK 再处理：ACK 完进程挂了，消息就丢了（RocketMQ 已经认为消费成功）。
  • catch 住异常返回 SUCCESS：消息被标记成功，永远不会重试，这是最隐蔽的丢消息方式。

5）重试机制详解

  • 重试队列：%RETRY%{ConsumerGroup}，每个消费者组一个。
  • 重试间隔：1s, 5s, 10s, 30s, 1m, 2m, 3m, 4m, 5m, 6m, 7m, 8m, 9m, 10m, 20m, 30m, 1h, 2h（共 18 个级别，默认重试 16 次）。
  • 超过 16 次 → 进入死信队列 %DLQ%{ConsumerGroup}，不再重试。
  • 死信队列要监控 + 人工处理，否则消息就永久躺在那儿了。

6）为什么说「绝对不丢」是做不到的

  • 同步刷盘 + 同步双写能极大降低丢失概率，但极端情况（机房断电、磁盘全坏、所有副本同时挂）仍会丢。
  • 而且全同步的代价是吞吐量断崖式下降。
  • 所以工程上的目标是「把丢失概率降到可接受的水平」+「有对账机制兜底」。

最终防线是业务层的对账：比如订单和库存每天对一次账，发现不一致就人工修复。任何 MQ 方案都需要业务对账兜底，这是很多面试官想听的答案。

追问预警
  • Q：异步刷盘 + 同步双写，会不会丢？
    A：如果 Master 和 Slave 都宕机（比如同一个机柜断电），会丢。但相比异步复制，概率低得多。要绝对不丢必须同步刷盘。
  • Q：SYNC_MASTER 会不会影响性能？
    A：会。每次发送都要等 Slave 的 ACK，RT 至少翻倍。而且 Slave 慢了会拖累 Master。所以要用异步刷盘 + 同步双写折中。
  • Q：消息重试 16 次后进死信队列，怎么处理？
    A：① 监控告警，人工介入；② 写个消费者订阅死信队列，把消息落库后人工修复；③ 分析失败原因，修复后重新投递。
  • Q：怎么验证消息没丢？
    A：① 生产端记录发送日志，消费端记录消费日志，用消息唯一 ID 对账；② 用 RocketMQ 的控制台看生产 TPS 和消费 TPS 是否匹配；③ 关键业务做日终对账。

29RocketMQ 消息堆积了怎么解决？

面试现场

先定位原因，再对症下药。原因无非三类：

  1. 消费速度变慢：消费逻辑里调了慢接口、做了复杂计算、数据库慢查询。
  2. 生产速度突增：大促、定时任务集中触发、上游重试风暴。
  3. 消费者本身出问题：消费者实例挂了、线程数不够、消费报错一直在重试。

排查手段：

  • RocketMQ 控制台：看 Topic 的堆积量（Diff 总量）、生产 TPS、消费 TPS。
  • 看消费位点：Consumer Offset 和 Broker Offset 的差值就是堆积量。
  • 看消费者日志：有没有大量消费失败、RECONSUME_LATER。
  • 看消费耗时：是不是某条消息处理特别慢（大 key、慢 SQL）。

解决方案：

一、提升消费能力（最直接）

  1. 增加消费者实例：注意上限是 Queue 的数量，超过就分不到队列了。
  2. 增加 Queue 数量（新建 Topic 时定好，已存在的 Topic 扩队列比较麻烦）。
  3. 提高消费线程数：consumeThreadMin / consumeThreadMax。
  4. 批量消费：setConsumeMessageBatchMaxSize(32)，一次拉多条，减少网络往返。
  5. 优化消费逻辑：异步化、批量入库、去掉不必要的远程调用。

二、限流降级（保护下游）

  • 生产端限流，削峰。
  • 消费端降级：非核心逻辑先跳过（比如先落库，后续异步处理）。

三、应急处理（堆积已经很大了）

  1. 临时扩容：加消费者实例 + 加 Queue + 提高线程数。
  2. 跳过堆积：如果是可以丢弃的消息（比如日志），直接重置消费位点到最新，跳过堆积。
  3. 新建消费者组：用一个新的 Consumer Group 从最新位点开始消费，老消息由专门的补偿任务慢慢处理。
  4. 临时转发：写个程序把堆积的消息转到新的 Topic，用更多的队列并行消费。
完整解析

1）为什么「加消费者」有上限

集群消费模式下，一个 Queue 同一时刻只能被一个消费者消费。

  • Topic 有 4 个 Queue，最多只能有 4 个消费者真正干活。
  • 第 5 个消费者会分不到队列，空转（Rebalance 后什么都不分到）。

所以扩容消费者之前一定要先看 Queue 数量。如果 Queue 只有 4 个，加到 10 个消费者也是白搭。

Queue 数量的经验值：Queue 数 >= 消费者实例数 × 每实例线程数（当然还要考虑 Broker 的承载能力）。

2）提高消费并发的几种方式

方式说明限制
加消费者实例最常用受 Queue 数限制
加 Queue需要重建 Topic 或扩队列已有 Topic 扩队列有成本
提高 consumeThreadMax单实例内并发受 Queue 数和 CPU 限制
批量消费consumeMessageBatchMaxSize消费逻辑要支持批量
消费逻辑异步化拉取和业务处理解耦复杂度上升，要处理背压

3）消费逻辑优化的具体手段

慢的原因排查清单：
□ 有没有同步调用外部 HTTP/RPC 接口？
□ 有没有单条 insert/update（应该改批量）？
□ 有没有慢 SQL（缺索引、大事务）？
□ 有没有锁竞争（比如同一行热点更新）？
□ 有没有大对象序列化/反序列化？
□ 日志打得太多（同步日志很慢）？

典型优化：把「消费 → 逐条写库」改成「消费 → 攒一批 → 批量写库」，吞吐能提升 10 倍以上。

4）重置消费位点（应急手段，慎用）

RocketMQ 控制台支持重置消费位点：

  • 按时间重置：跳到某个时间点的位点。
  • 按位点重置：直接指定 offset。
  • 跳过堆积：跳到当前最新位点，放弃所有堆积消息。

风险：跳过的消息永久丢失，只适用于「消息可以丢」的场景（日志、统计类）。

5）新建消费者组方案（推荐用于「不能丢但要快速恢复」）

1. 新建 Consumer Group B，从最新位点开始消费 → 保证新消息不堆积
2. 老 Consumer Group A 继续消费堆积消息（或者由补偿任务处理）
3. 堆积清完后下线 A

这样新消息不受影响，老消息慢慢补，业务影响最小。

6）生产端的削峰

  • 限流：Sentinel 对发送端限流。
  • 消息合并：把短时间内的多条小消息合并成一条大消息。
  • 延迟消息：非实时消息用延迟消息错峰发送（RocketMQ 支持 18 个延迟级别）。
  • 大促前预估：提前扩 Queue 和消费者。

7）监控告警（预防大于治疗）

必配的告警：

  • 堆积量超过阈值（比如 10 万条）→ 告警。
  • 消费 TPS 持续低于生产 TPS → 告警。
  • 死信队列有消息 → 告警。
  • 消费 RT 上升 → 告警。

8）总结一张应急处理流程图

发现堆积
  ↓
① 看 Queue 数 vs 消费者数 → 消费者数 < Queue 数？ → 加消费者实例
  ↓
② 消费者数已 = Queue 数 → 看消费耗时 → 优化消费逻辑（批量、去远程调用）
  ↓
③ 逻辑没法再优化 → 扩 Queue（重建 Topic 或新建 Topic 迁移）
  ↓
④ 还来不及 → 应急：能丢的重置位点跳过；不能丢的新建消费者组先保新消息
  ↓
⑤ 事后：复盘原因，加监控告警，做容量规划
追问预警
  • Q：Queue 数能不能动态增加？
    A：可以，但新加的 Queue 只会被新的消息使用，老 Queue 里的消息还在。而且扩容后需要 Rebalance，消费者要重新分配队列。一般建议建 Topic 时就定好 Queue 数，比如按「未来 2 年的峰值消费者数」来估。
  • Q：Rebalance 会有什么问题？
    A：Rebalance 期间消费会短暂停顿（队列重新分配）。频繁 Rebalance（比如消费者频繁上下线）会导致反复停顿 + 重复消费。所以要保证消费者实例稳定，避免网络抖动。
  • Q：怎么判断是消费慢还是生产快？
    A：看控制台的生产 TPS 和消费 TPS 曲线。生产 TPS 平稳但消费 TPS 下降 → 消费慢；两个都涨 → 生产突增。
  • Q：堆积多少算严重？
    A：没有绝对标准，看业务。经验值是堆积量 × 单条处理耗时 > 可接受延迟就要处理了。比如单条处理 10ms，堆了 100 万条，那就要 10000 秒（2.7 小时）才能消化完。

30RocketMQ 如何保证幂等性？如何确保消息不被重复消费？

面试现场

先给一个必须说清楚的结论：RocketMQ 不保证消息不重复，它保证的是 At Least Once（至少一次）。

为什么会重复：

  1. 生产端重试：发送超时但 Broker 实际收到了，Producer 重试 → 两条消息。
  2. 消费端 ACK 丢失：消费成功了，但返回 ACK 时网络断了，Broker 认为没消费成功，重新投递。
  3. Rebalance：消费者重新分配队列时，正在处理但没 ACK 的消息会被重新投递。
  4. 消费失败重试：业务处理了一部分，然后失败，重试时会再处理一遍。

所以「不重复消费」在 MQ 层面是做不到的，只能在业务层做幂等。

幂等的几种实现方案：

  1. 唯一索引（最简单可靠）：给业务表加唯一索引，比如 订单号 + 状态，重复插入直接报错，捕获异常忽略。
  2. 去重表 / 消息表：单独一张表记录处理过的消息 ID，处理前先查（配合唯一索引，靠数据库保证原子性）。
  3. Redis 去重：SET messageId 1 NX EX 86400，设置成功才处理。注意要考虑 Redis 挂了怎么办。
  4. 状态机 / 版本号：更新时加状态条件，比如 UPDATE ... WHERE status = '待支付'，影响行数为 0 就说明已经被处理过了。
  5. 分布式锁：按业务 key 加锁，同一时刻只有一个线程处理。

我一般首选「唯一索引 + 状态机」，因为不依赖外部组件，最可靠。Redis 去重作为第一层拦截，减少数据库压力。

完整解析

1）为什么 ACK 丢失会导致重复

Consumer 处理消息成功
  ↓
Consumer 返回 CONSUME_SUCCESS
  ↓ ← 网络断了，Broker 没收到
Broker 认为消费失败，等待重试
  ↓
Consumer 再次收到这条消息 → 重复消费

这就是「处理成功但确认失败」的经典场景，无法避免，只能靠幂等。

2）四种幂等方案详细对比

方案原理优点缺点适用
唯一索引数据库约束最可靠、无额外组件需要业务字段有唯一性首选
去重表记录已处理消息 ID通用每次多一次查询/写入消息无业务唯一键
Redis 去重SETNX性能高Redis 挂了失效，可能误判第一层拦截
状态机更新时带状态条件无额外开销只适用有状态流转的业务订单类业务
分布式锁按 key 加锁简单性能差，锁超时问题兜底

3）唯一索引方案代码示例

// 业务表：unique key (order_no, message_type)
try {
    orderRecordMapper.insert(record);
} catch (DuplicateKeyException e) {
    // 已经处理过，直接忽略
    log.warn("重复消息，已忽略, orderNo={}", record.getOrderNo());
}

要点：靠数据库的唯一约束来保证原子性，不要用「先 select 再 insert」——那有并发窗口。

4）状态机方案代码示例（订单场景）

-- 只有「待支付」状态才能改成「已支付」
UPDATE orders SET status = 'PAID', pay_time = NOW()
WHERE order_no = #{orderNo} AND status = 'PENDING';

-- 影响行数 = 0 说明：
--   a) 订单不存在
--   b) 订单已经是 PAID 了（重复消费）
-- 两种情况都不需要再处理
int affected = orderMapper.updateStatus(orderNo, "PAID", "PENDING");
if (affected == 0) {
    log.info("重复消费或状态不匹配，跳过, orderNo={}", orderNo);
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;   // 直接 ACK，不重试
}

这个方案的精妙之处：把「幂等判断」和「业务更新」合并成一次原子操作，不需要额外的查询。

5）Redis 去重的坑

// 看起来没问题，但有两个坑
String key = "msg:" + messageId;
Boolean success = redis.setIfAbsent(key, "1", Duration.ofHours(24));
if (Boolean.TRUE.equals(success)) {
    // 处理业务
    doBusiness(msg);
} else {
    // 重复，跳过
}

坑一：Redis 挂了或者数据丢失 → 去重失效，会重复处理。所以 Redis 只能当第一层，数据库唯一索引才是最终保障。

坑二：业务处理失败但 key 已经写了 → 消息重试时会被当成重复而跳过，导致消息丢失！

正确做法：先处理业务，成功后再写 Redis；或者用「处理中/已完成」两阶段标记，处理失败要删掉 key。

// 更好的做法
if (!redis.setIfAbsent(key, "PROCESSING", Duration.ofHours(24))) {
    return CONSUME_SUCCESS;   // 重复消息
}
try {
    doBusiness(msg);
    redis.set(key, "DONE", Duration.ofHours(24));
} catch (Exception e) {
    redis.delete(key);        // 关键：失败要删掉标记，允许重试
    return ConsumeConcurrentlyStatus.RECONSUME_LATER;
}

6）幂等设计的三条原则

  1. 幂等是业务的职责，不是 MQ 的职责。任何 MQ 都做不到「不重复投递」，只能做到「不丢」。
  2. 优先用数据库的唯一约束，因为它是最可靠的（数据库的 ACID 保证）。
  3. 幂等键要选对：应该用业务唯一标识（订单号、流水号），而不是 messageId。因为重试消息的 messageId 是新的（生产端重试会生成新消息），而业务标识不变。

第 3 点特别重要，很多人用 messageId 做幂等键，结果生产端重试产生的两条消息 messageId 不同，幂等失效。

7）哪些场景天然幂等

  • UPDATE t SET status = 'PAID' WHERE id = 1：天然幂等（执行多次结果一样）。
  • UPDATE t SET count = count + 1：不幂等（每次都会加）。
  • INSERT：不幂等（除非有唯一索引）。

所以对于计数类的更新，要用「带条件的更新」或者「记录明细 + 汇总计算」来保证幂等。

8）消息重试时要注意「部分成功」

// 危险：两条消息处理，第一条成功，第二条失败
for (MessageExt msg : msgs) {
    processA(msg);    // 成功
    processB(msg);    // 失败 → 返回 RECONSUME_LATER
}
return ConsumeConcurrentlyStatus.RECONSUME_LATER;
// 重试时 processA 会再执行一次 → 必须幂等！

批量消费时，任何一条失败都会导致整批重试，所以 processA、processB 都必须幂等。

追问预警
  • Q：为什么不用 messageId 做幂等键？
    A：因为生产端重试会生成新的 messageId（每次发送都是新消息）。幂等键要用业务唯一标识，比如订单号 + 业务类型。如果一定要用 messageId，得保证发送端不重试或者用业务字段做 key。
  • Q：RocketMQ 有内置的幂等支持吗？
    A：没有。RocketMQ 只保证 At Least Once。Kafka 0.11 之后有幂等生产者（PID + Sequence Number）能保证生产端不重复，但消费端仍需业务幂等。
  • Q：At Least Once、At Most Once、Exactly Once 有什么区别？
    A：At Most Once：最多一次，可能丢，不重复（发完不管）；At Least Once：至少一次，不丢但可能重复（RocketMQ 的语义）；Exactly Once：精确一次，不丢不重（需要业务幂等配合才能实现，MQ 本身做不到）。
  • Q：怎么测试幂等性有没有做对？
    A：① 手动重复发送同一条消息（用同一个业务 key），看业务表有没有产生重复数据；② 消费端故意抛异常触发重试，看数据是否正确；③ 压测时模拟网络抖动，看有没有脏数据。

附：面试答题的通用框架

答题结构

不管问什么，都按这个顺序组织：

  1. 一句话给结论：先让面试官知道你的答案方向是对的。
  2. 分点展开：一般 3~5 点，每点一句话概括 + 一句解释。
  3. 给场景或数据：说出你在哪个项目里用过、效果怎么样、踩过什么坑。
  4. 主动说边界：这个方案的局限是什么，什么情况下不适用。

第 4 点最加分，因为它说明你不是背答案，而是真的理解。

常用句式

  • 「这个问题的核心是……」
  • 「我从三个方面回答……」
  • 「严格来说……但工程上一般……」
  • 「我们项目里是这么做的……效果是……」
  • 「这个方案的局限是……所以如果场景变成……我会换成……」

不会的问题怎么答

不要硬编。可以这么说：

「这个点我了解得不深，我的理解是 A，但不确定对不对。我平时遇到类似问题会去查官方文档和源码，比如我会先看 XX。您能指个方向吗？」

面试官考的是思考方式，不是知识库。承认不知道 + 展示学习路径，比胡编强得多。

需要提前准备的「项目故事」

准备 3~5 个能讲 5 分钟的项目案例，每个都包含：

  • 背景：什么业务、什么规模（QPS、数据量）。
  • 问题：遇到了什么（慢、崩、数据不一致）。
  • 方案：为什么选 A 不选 B。
  • 结果：用数字说话（RT 从 500ms 降到 50ms，QPS 从 1000 提到 5000）。
  • 反思：如果重来会怎么改进。

面试里所有八股最终都会落到「你项目里怎么用的」，这才是区分「背题的」和「做过的」的关键。
